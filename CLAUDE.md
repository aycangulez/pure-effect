# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm test                                          # run all tests
npx mocha test/all.js --grep "pattern"            # run a single test by name
npm run format                                    # Prettier over index.js, index.d.ts, examples/*.js, scripts/*.js, test/all.js, test/types.test-d.ts, README.md, CLAUDE.md, CHANGELOG.md, CONTRIBUTING.md
npx tsd                                           # type-level gate over test/types.test-d.ts
npx tsc -p jsconfig.json                          # strict tsc over index.js, test/all.js, test/types.test-d.ts, examples/*.js, and scripts/*.js, reading index.d.ts as a consumer; the same config VS Code uses
npm run test:ts-minimum                           # compiles index.d.ts and test/types.test-d.ts with TypeScript 5.1, the oldest the declarations support
npm run generate                                  # rewrites effectPipe's overloads in index.d.ts from scripts/effect-pipe-overloads.js
npx esbuild index.js --minify --format=esm | gzip -9 | wc -c    # the size the README claims
npx stryker run                                   # mutation testing: mutates index.js, runs test/all.js against each mutant; report in reports/mutation/
```

There is no build or lint step: the library ships as plain ES modules. Formatting is Prettier, configured in `.prettierrc`. CI (`.github/workflows/ci.yml`) runs `npm test` on Node 22, 24 and 26, Prettier's check, and `npm run test:ts-minimum`, on pull requests and on pushes to `main`. The TypeScript 5.1 check stays out of `npm test` because a second TypeScript installed as a dev dependency links its own `tsc` over the one the gate runs, so it fetches 5.1 with `npx` instead and needs the network the first time. **Check `npm test` by its exit code**: a `tsd` failure prints neither "passing" nor "failing", so grepping the output for those words hides it. After a structural edit to `index.d.ts`, compare the runtime exports against the declared ones rather than trusting the diff. `package.json` has a `files` list, so anything new that must ship has to be added there, and `npm pack --dry-run` shows what would be published. `CONTRIBUTING.md` restates the rules for a human contributor and does not refer to this file, so it reads on its own; a new rule goes in both, a new reason only here.

**Mutation testing** stays out of CI: its survivors need reading rather than counting, so it sets no score to fail on, and a run is much slower than the rest of the gate. Run it after changing `index.js` or its tests, since a test that passes whatever the code does is invisible to every other check. Its survivors are not a to-do list. Most are equivalent mutants that change nothing observable (optional chaining on an `AbortController` that always exists, arrays sized in advance and then filled, `performance.now()` against `Date.now()`, `chain` cases that fall through into identical code, a check after a retry backoff that the loop repeats) or message wording, and a few flip between runs because some tests depend on timing. Two gaps are left on purpose: whether each nested `Parallel` removes its listener from the enclosing signal, and the exact wording of `timeTravel`'s narration. Before calling a survivor new, apply the mutant by hand to the old code and the new and run the suite: a flip between runs is noise, and a mutant that survives both is an old gap rather than a regression. A survivor outside those classes is a behaviour no test pins, which is what the run is for.

## House rules

**The size figure lives in one place.** The README's feature bullet states the minified, gzipped size in prose; re-measure with the command above after changing `index.js` and reword it when the number moves. The size badge, `img.shields.io/bundlejs/size/pure-effect`, measures the latest published version with esbuild, the same tool, so it corrects itself after a publish; Bundlephobia's badge was not used because it measures with webpack and terser and is often rate limited. **A commit message and a changelog entry never mention the size.** Both are read long after the fact, when the number is stale and the reader cannot tell, and neither is what they are for: a changelog says what changed for a user, and a commit message says why.

**A changelog entry and a commit message leave out documentation-only changes.** A correction to the README, the JSDoc or this file changes nothing the library does, so a changelog, which says what changed for a user of the library, has nothing to report; and a commit message, which says why the code changed, would only restate the diff by listing the documents updated alongside it. So a docs change that ships with a behaviour change goes unmentioned in both, and one that ships alone gets no changelog entry. A commit that changes only documentation still needs a message, and it says why the docs changed.

**The README's `Load Tests` section is re-measured by nothing.** It reports experiments run in September 2026 with scripts that are not in this repository. Its counts stay true until behaviour changes, and its timings go stale with the machine. A change to what it claims (isolation between concurrent runs, replay fidelity, memory held across runs, `Parallel`'s limit and ordering) means rerunning an equivalent experiment and updating the section, or cutting the claim. It carries no size figure.

**Markdown prose has no hard line breaks.** Write each paragraph and list item as one line and let the editor wrap it, since hard breaks turn a one-word edit into a reflowed paragraph. `proseWrap: never` unwraps anything that arrives wrapped, but write it unwrapped in the first place. Code blocks and table rows are untouched.

**No jargon in the README.** A reader meets the library there and should not need vocabulary from functional programming, from the interpreter's internals, or from this file. The names the library exports are not jargon (`Command`, `Retry`, `Parallel`, `Resolver`, `TimeParadox`, `onStep`, `backoff` and the rest), and everything else gets the plain word. A flow, not an Effect tree. Part of a flow, not a node or a subtree. The Command's function, or `cmd`, not a thunk. Joining, not fan-in. Stops, not short-circuits. A request, not cooperative. Attached, not stamped. Does the same thing again, not deterministic. No catch, not no catch combinator. Runs at the same time, not concurrently, wherever nothing turns on the distinction. `grep -rniE "thunk|combinator|monad|kleisli|effect tree|fan-in|fan-out|short-circuit|cooperative|imperative shell|arity|stamp" README.md` should print nothing. A precise term may stay if the plain words follow it in the same breath, as `idempotent (safe to run more than once)` does in the Retry section; a term that needs a gloss every time it appears is one the README should not use. The precise words are fine everywhere else: this file, JSDoc, code comments and test names.

**No em dashes.** The `—` character appears nowhere in the repository: not in the README, this file, JSDoc, comments, test names or assertion messages. Use the punctuation that carries the relationship: a colon when the second half explains the first, parentheses for an aside, a semicolon between linked clauses, a comma for a light pause, and a full stop when the clause can stand alone, which is usually the honest fix. Nothing enforces it; `grep -rn "—" --include="*.js" --include="*.ts" --include="*.md" .` checks a change before it lands. A table cell that needs a placeholder uses `n/a`.

**Name a condition when it's used more than once, or when you'd otherwise need a comment to say what it means.** This applies to `index.js`. A concept written inline drifts into spellings that each have to be checked against the others: "a non-null object" was spelled three ways across six places before `isObject` replaced them. A condition one function uses once can be a named `const`, as `pastTheEnd` and `haltedByReplay` are. Make a predicate a type guard (`@returns {value is T}`) only where a caller needs the narrowing, as the interpreter loop does with `isPending`: a guard to `object` on a value typed `any` narrows it to `object`, and reading a property off it stops compiling, which is why `isObject` returns a plain `boolean`.

## Design

**pure-effect** is a zero-dependency effect system for JavaScript implementing the "Functional Core, Imperative Shell" pattern. Business logic returns plain data instead of executing side effects, so it can be tested without mocks, and because a flow is inert data until the interpreter walks it, a recorded run can be fed back through the interpreter with no I/O at all. Everything is in `index.js`, and `index.d.ts` declares it.

### Primitives

| Export | Shape | Purpose |
| --- | --- | --- |
| `Success(value)` | `{ type: 'Success', value }` | Wraps a successful result |
| `Failure(error, initialInput)` | `{ type: 'Failure', error, initialInput }` | Stops the pipeline |
| `Command(cmdFn, nextFn, meta)` | `{ type: 'Command', cmd, next, meta }` | Defers a side effect for the interpreter; `meta.name` sets the Command's identity |
| `Ask(nextFn)` | `{ type: 'Ask', next }` | Reads the `context` passed to `runEffect` |
| `Retry(effect, options)` | `{ type: 'Retry', effect, options, next }` | Runs a tree again after an I/O fault; a per-use `onExhausted` runs a fallback when every attempt has failed |
| `Parallel(effects, next?, options?)` | `{ type: 'Parallel', effects, next, options }` | Runs trees at the same time; the first branch to fail cancels the others unless `settled`; `limit` caps how many run at once |
| `effectPipe(...fns)` | n/a | Composes steps into a pipeline through `chain` |
| `runEffect(effect, context, callConfig?)` | async | Runs a flow; a per-call `callConfig` merges over the installed hooks, or replaces them under `inherit: false` |
| `configureEffect(...configs)` | n/a | Adds a layer of process-wide hooks (`onStep`, `onRun`, `onBeforeCommand`) and returns a function that removes it |

`Command`'s `next` is optional and defaults to `(result) => Success(result)`, since most Commands pass their result straight through, and `Parallel`'s defaults to `(values) => Success(values)`. `Parallel`'s second argument is `next` or the options, whichever it looks like, so `Parallel(effects, { limit: 5 })` needs no placeholder, and `undefined` or `null` there is a skipped `next`, so options passed third still count (they were once dropped, which ran a settled batch unlimited and let one failure cancel it); `replayEffect` tells a `Resolver` from a trace by `typeof` the same way. The README's `Composing Larger Flows` section shows the patterns the primitives already support (branching into sub-pipelines, joining `Parallel` results, small local joins, written as named steps, that carry a minimal value shaped for their purpose), which is why no combinators were added for them. Its advice against a growing accumulator object is bug avoidance rather than taste: an accumulator hides which step depends on what, lets stale fields outlive the steps that produced them, and widens what carries PII, so keep the examples threading minimal values.

**Command identity** comes from the internal `commandName(eff)`: a non-empty string `meta.name`, else `cmd.name`, else `'anonymous'`. Trace entries are keyed on it, replay matching compares it, and telemetry spans are titled with it, which is why it is one function. `meta.name` exists because `cmd.name` alone made recording depend on syntax: an inline arrow recorded as `'anonymous'`, and a minifier that mangles names renamed every step, both silently. `cmd.name` stays supported and is what the examples use.

### Composition and `initialInput`

`chain` (internal) connects a node to the next pipeline step: `Success` passes its value on, `Failure` stops, and `Command`, `Ask`, `Retry` and `Parallel` wrap their continuations, carrying `Retry`'s `effect` and `Parallel`'s `effects` over untouched. `chain` checks what each step returns, which is the only place the step's name (`fn.name`) is known and so where the useful error message comes from, and it checks `effect == null` before reading `.type`, so a missing return is named rather than thrown as a bare `TypeError`.

Every `Failure` carries `initialInput`, the input of the flow that was called, at any depth, alongside the full error; neither is trimmed, since a test and a developer both need the whole thing. Two mechanisms make that hold, and both are needed. `chain` stamps every node but a `Success` with the pipeline's start, overwriting a sub-pipeline's own, and `effectPipe` ends with an identity pass, `chain(tree, Success, start)`, so the last step's continuations are stamped too; this is what holds for a tree walked by hand in a test. And the interpreter restamps the final `Failure` with the root's input, since the subtrees a `Retry` or `Parallel` holds are run directly rather than reached through a continuation; this is what holds for a run. The outcomes a settled `Parallel` hands `next` never pass that boundary, so each keeps its branch's own input, or none: that input identifies the failed record, and stamping the flow's input onto each would copy a registration's credentials into every one. A `Success` is never stamped, so `assert.deepEqual(result, Success(v))` holds whatever shape the flow had. Only `effectPipe` puts the input on the tree, so a flow whose root is a bare `Command`, `Ask`, `Retry` or `Parallel` carries none and a hook-based recorder records none; the README says to wrap such a flow in a one-step pipeline, since no hook can recover an input that only a closure holds. `recordEffect` takes the input as an argument and does not rely on the stamp.

PII control is split: `redact` is the single mechanism for a trace, and the shell owns what reaches logs, so the guidance is to log `result.error` rather than a whole `Failure`, and to report the `Failure`s a settled `Parallel` hands `next` the same way, since each carries its branch's input.

### The interpreter

`runEffect` is a thin public wrapper over the private `interpret`, which `replayEffect` also calls. Inside it, `execute` walks a subtree in a `while` loop, resolving `Ask` itself and handing every other node to `runRetry`, `runParallel` or `runCommand`. Each returns a `Success` carrying the value for the node's `next`, or the `Failure` or I/O fault that stops the subtree. `onRun` wraps the whole run once, `Retry` attempts included. The loop's condition, `isPending`, reads the type as `value?.type`, so a continuation that returned `undefined` reaches the `EffectTypeError` at the end of `execute` instead of throwing from the condition.

**Three kinds of failure.** This distinction answers a family of bugs, and most of what follows depends on it. A `Failure` a step returned is an **abort**: the flow has decided, and the shell acts on it. A throw from a Command's function is an **I/O fault**, which is what `Retry` exists for. An `EffectTypeError`, a replay fault, or a throw from a continuation or a pure step is a **harness error**, not an outcome, and `runEffect` rejects with it. Without the distinction `Retry` re-ran a lookup whose answer could not change, wrapped a domain error in an exhaustion it had nothing to do with, and let `onExhausted` answer a deliberate abort. An I/O fault is an internal state, `{ type: 'IoFault', error, initialInput }`, which only `execute` and its per-node functions return; it becomes a plain `Failure` wherever it would reach user code, at the `runEffect` boundary and in the outcomes a settled `Parallel` hands `next`. So every `Failure` user code holds is plain data, whatever a step returns is an abort, and a continuation cannot forge a fault, since the loop accepts only the six public types. Keep provenance out of anything user code can hold: it was once a hidden symbol on the `Failure`, and composition kept or dropped it depending on the pipeline's shape. The rule underneath is the README's: a domain outcome is returned, never thrown, so a `cmd` function that throws a business error has told the interpreter it was an I/O fault, and the interpreter acts on that.

**Where a throw comes from.** `runCommand` has two regions, and `next` runs outside both, because a throw means something different in each. A throw from `onBeforeCommand` is an abort, since a veto stops the flow rather than the I/O failing. A throw from the step runner is an I/O fault unless the Command's function had already succeeded: `op` records that, and then the throw is a bug in an `onStep` hook and rejects the run, since retrying would repeat work already done (a telemetry exporter failing after a charge went through once charged the card on every attempt). A hook that calls `op` and returns `undefined` when the function returned a value rejects the run with a `TypeError`: a metrics hook that forgot its `return` turned a found user into `undefined`, saved a duplicate account, and left a recorder inside it holding the real answer, so the trace contradicted production. Only `undefined` is refused, so a hook that returns a copy still works, and a hook that never called `op` is not checked, since that is how replay answers. A hook that throws without calling `op` stays a fault, because that is how replay reports a recorded error and how a circuit breaker written as a hook refuses a call; in a `hooks: true` replay a hook that throws after a replayed step therefore counts as a fault, which is harmless, since nothing executes. `next`, with every pure step it reaches up to the next Command, runs in `execute` after `runCommand` has returned, so a throw there rejects the run, as a throw from any other continuation does. A harness error carries the `harnessError` symbol, always on an `Error` the library created and never on flow data, so both catches rethrow it. `op` is async, so a hook always gets a promise, even for a synchronous function, as the `StepRunner` type and the README's "must `await op()`" promise. The `Where a throw comes from` suite pins each region.

**Malformed flows.** `asEffect` and `effectTypeError` reject anything that is not an Effect with a message naming its source and the likely mistake (`describeValue`): a missing return, `null`, an `async` step, which is named as a Promise and pointed at a Command, a flow passed without its input, or an unrecognised `type`. A malformed flow is a bug and throws; a Command that rejects is a domain outcome. The constructors check their own arguments as the flow is built, with `describeArgument`, which calls a missing argument `undefined` rather than a missing return and names an Effect in the wrong place by its type, so a mistake is reported before the I/O it would have run: `Command(db.findUser(email))` ran the query while the flow was built and was then retried as an I/O fault, and `Command(fn, { name })` charged the card before rejecting with `effect.next is not a function`. A `null` next counts as omitted in `Command`, as in `Parallel`. `malformed` builds every `EffectTypeError` and attaches a handler to a native `Promise` it reports, so a throwing async step does not crash the process after the caller has caught the error. Only a native `Promise`, because calling `then` on a Knex or Mongoose query builder runs the query.

**Retry.** Options are per-use and merged over `attempts: 3`, `delay: 100`, `backoff: 1`. An option set to `undefined` keeps its default, since that is how an absent config key arrives, `attempts` must be a positive integer, and `delay` and `backoff` must be finite numbers of 0 or more, checked when the `Retry` runs: an undefined `backoff` once made every wait after the first `NaN` milliseconds, which is no wait at all. An abort passes through at once, unretried and unwrapped, and `onExhausted` never sees it. An I/O fault is retried, and when attempts run out the result is `{ retryExhausted, lastError, attempts }`, itself an I/O fault so that an enclosing `Retry` retries this one. `onExhausted` runs a fallback Effect under the retry's `f` path prefix: its success feeds `next`, its failure propagates unwrapped, and it never starts in a cancelled branch. Each attempt runs the **entire** wrapped tree again, including Commands that already succeeded, and a Command's `next` is part of that tree, so `Retry(Command(cmd, next))` where `next` continues the flow wraps everything downstream: a booking saga with two such nested retries charged a card nine times. The rule is that a retried Command keeps its default `next` and the branching happens in a later pipeline step, as the README, the JSDoc and the second `Documented sharp edges` test say. Catching and retrying are alternatives: a miss caught inside the `cmd` function and returned as a value is an abort, so a `Retry` around it makes one call and never tries again, and the README says to catch when the flow should handle the outcome as data and to let it throw when `Retry` should act on it.

**Parallel.** Branches run through `runBounded`: `Promise.all` without a `limit`, and a pull-by-index worker pool with one, so results and paths follow array order either way. Under `limit: 1` the pool is a sequential loop that stops at the first failure, which is how the README's `Coming from async/await` translates a `for` loop, in two parts: a step that gets the list, then a `Parallel` that maps over it. A test therefore pins the order branches start in as well as the order results return. By default the first branch to fail, or to throw, cancels the others, and its `Failure` is the result, with `next` skipped. Under `settled` a failing branch cancels nothing and `next` receives every branch's outcome as a plain `Success` or `Failure` in array order, while a throw still cancels the others and rejects the run: `settled` catches outcomes that were always possible, not mistakes. `limit` and `settled` are per-use, since they describe the resource and the batch rather than the process, and a limit never reaches a trace, since paths come from array index. The whole `Parallel` is one `onStep` step of type `'Parallel'` whose `op` runs the branches and returns the decision, which branch if any cancelled the others, so the decision is recorded and a replay can hand it back. A hook must call that `op`, and the interpreter rejects with a `TypeError` when a hook returned without letting it run. A branch's throw is held until every branch has settled and rethrown after the step returns, so the decision is recorded and no branch is left running unobserved. `runBranches` picks the rule for whether a settled branch cancels the others (a throw, or a failure unless `settled`, when live; nothing when reproducing a recorded cancellation), hands it to `settleBranches`, and then either checks the recorded decision or builds one from timing. The branch that cancelled the others is tracked apart from the branches that failed because they were cancelled, so a cancellation never displaces the real error. A fail-fast `Parallel` drops the values of the branches that succeeded, so undoing one of them, such as refunding a charge when the stock ran out, is a settled `Parallel` whose `next` returns the undo steps and then fails; the README's `Running Effects in Parallel` section teaches it, since the checkout experiment left a charge nobody could refund.

**Cancellation is a request.** Each `Parallel` has an `AbortController` linked to the enclosing one by `linkedScope`, so cancellation nests. A cancelled branch starts no further Commands: that is checked at the top of `execute`'s loop, again once `onBeforeCommand` returns, since an interceptor such as a rate limiter can wait while a sibling fails (a charge once started 40ms after its branch was cancelled), and again before a `Retry` fallback. A retry backoff ends at once when its branch is cancelled, including one that starts on a signal that has already fired, which is the usual case, since a Command that honours the signal rejects the moment a sibling fails; `delayFor` checks `aborted` first because a listener added to an aborted signal never runs. Stopping the Command already in flight needs its function to pass on the `AbortSignal` it is handed, which is why `cmd` receives the signal inside a `Parallel` and no argument anywhere else. The signal is the first argument, so a function passed by name with an optional first parameter, such as `nanoid(size = 21)`, takes the signal for it: a documented sharp edge, which TypeScript refuses to compile. A function that ignores it runs to completion, so a branch's first Command can still write after a sibling has failed, and a pinning test covers that. `Parallel` still awaits every branch before returning. The trigger is the first failure to finish, which is completion order: a synchronous throw beats a promise that rejects a microtask later, whatever their positions, and branches that fail without I/O finish in array order, which is pinned.

### Hooks and `configureEffect`

- `onStep(name, type, op, path)` wraps each Command's execution and each `Parallel`'s branches. It decides whether the Command runs at all, which is how replay suppresses I/O, so a hook that only watches must `await op()` and return its result; one that returns `undefined` after `op` returned a value makes the run reject.
- `onRun(effect, op, flowName)` wraps a whole run, once; `flowName` is `context.flowName`, or `''`.
- `onBeforeCommand(command, context)` runs before each Command, and throwing from it vetoes the Command as an abort.

`configureEffect` is additive. Each call adds one layer and returns a function that removes that layer wherever it sits, idempotently, and several configurations passed to one call form one layer, which is the same as installing them separately. A call with no arguments at all removes every layer, which is how the suites reset; a call whose arguments are all `undefined`, such as `configureEffect(flag ? hooks : undefined)`, is a conditional install that adds and removes nothing. `chainHooks` merges the layers into `globalConfig`, earliest outermost: `onStep` and `onRun` are wrappers that nest, so a thrown Command unwinds from the innermost hook back out, and `onBeforeCommand` interceptors run in order. Keep those semantics if the hook shapes change. A slot no layer defines is absent, and `interpret` picks the library default where it reads the slot. A per-call `callConfig` is merged over the installed wiring by the same merge, innermost, or over nothing under `inherit: false`, and a non-boolean `inherit` throws rather than being coerced. That is why `recordEffect` inside an instrumented application keeps its spans, and why `replayEffect` passes `inherit: hooks`: under `hooks: true` its resolver sits innermost and the configured hooks observe a replay that still executes nothing. Merging is only trustworthy while every nested hook is a watcher, since a global `onStep` that never calls `op` would starve an inner one. Anything that wraps `onStep` passes `path` on as the fourth argument: a wrapper that drops it records a trace without paths, which cannot replay a `Parallel`, and in TypeScript it no longer compiles, since `StepRunner` declares `path` as present. Only the innermost hook can pass `op` an argument, the recorded decision, since `chainHooks` hands outer hooks a closure that takes none; replay's hook is per-call, and so innermost. A leftover `retry` key throws from `configureEffect` and from `callConfig`, checked before any layer is installed; it is migration scaffolding and comes out at 1.0.

`observeSteps(handler)` (internal) is the contract for a hook that only watches: `op` always runs, its result is returned, its error propagates, and anything the observer throws is dropped. It exists because the raw hooks let a throwing `redact` turn a successful run into a `Failure`. Keep it minimal: `recorder` is its only caller and needs only `onStep`. The `durationMs` on each trace entry comes from it, rounded to microseconds.

### Recording and replay

| Export | Purpose |
| --- | --- |
| `recorder(options?)` | Returns `{ onStep, entries, toTrace }`; the `onStep` hook records every Command's result or error, and each `Parallel`'s decision. Options: `redact`, `maxEntries`, `stack` |
| `recordEffect(flowFn, initialInput, opts?)` | Runs a flow for real while recording; returns `{ result, trace }`. Convenience for tests and scripts |
| `replayEffect(effect, traceOrResolver, opts?)` | Replays a flow, feeding recorded outcomes to Commands instead of running them. Takes a trace or a `Resolver`; returns `{ result, unreached }` for a trace and `{ result }` for a `Resolver`. Options: `context`, `fastRetry`, `hooks`, `onMissing`, `onResolved` |
| `timeTravel(flowFn, traceLog, options?)` | Narrated replay: rebuilds the flow from the recorded input, logs each step, warns on a version mismatch, and names unreached steps; returns the bare outcome |

The four are a 2x2: `recorder` and `replayEffect` are the capabilities, at the hook and flow level, and `recordEffect` and `timeTravel` are the convenience pair that also own the trace metadata. That metadata is why the conveniences exist: `initialInput` rebuilds the flow, `context` lets `Ask` resolve on replay, and `version` flags a stale trace. `replayEffect` defaults its `context` to the trace's, since an `Ask` gate replayed with another context takes another branch and nothing flags it; an explicit `context` wins, a `Resolver` has none to offer, and a trace assembled by hand without one replays against an empty context. `fromTrace` (internal) turns a reference-format trace into a `Resolver` and reports each entry it hands out, which is how `replayEffect` computes `unreached`. `TraceLog` is the reference format, not a contract, since a `Resolver` supports any storage shape.

Recording is an `onStep` hook, so it needs no change at call sites: give each run its own recorder, as the reference wiring does, or pass one per call. A single `recorder()` installed for the process holds every run's steps, so its trace has duplicate paths and a replay refuses it; the README and JSDoc once advised exactly that. Seven invariants hold replay together, and breaking one breaks it in ways tests may not catch:

- **Replay drives the real interpreter and never touches the flow.** `replayEffect` runs the flow through `interpret`, so `Ask`, `Retry` and `Parallel` replay exactly as they run, and replaces only the interpreter's two ways of reaching outside the flow: I/O, through an `onStep` that answers from the trace instead of calling `op`, and waiting, through `fastRetry`, which waits no time between retry attempts (still a wait, so branches replayed by timing interleave as they would with a delay). The interpreter's only execution point is `await localStepRunner(cmdName, 'Command', op, cmdPath)`, and replay's `onStep` never calls `op` unless `onMissing: 'execute'`, so **no side effect can occur by default**; a Command executed anywhere else would be invisible to recording and replay alike. `hooks` defaults to `false`, so a replay cannot reach a telemetry backend or a guardrail that performs I/O, and under `hooks: true` the hooks see the flow's own nodes.
- **Steps match by path.** A step's `path` is its position in the tree, numbered within a subtree, with each `Parallel` branch and `Retry` attempt opening its own prefix: `0p1/0r2/0` is branch 1, attempt 2, first Command, and a fallback opens `0rf/`. It depends only on the tree's shape, so it is independent of finishing order and still detects a changed flow. `fromTrace` matches by path whenever every entry has one, and refuses duplicate paths. A trace without paths, recorded before they existed or written by hand, is matched in order, each entry checked against the Command the flow asks for; that is exact for sequential flows, and a step inside a `Parallel` is refused, since an answer by position there is right only when the replay happens to finish in production's order.
- **A cancelled `Parallel` replays its recorded decision.** Timing decides which branch cancels a `Parallel`, so the decision is recorded as the `Parallel`'s own entry at its path (`0p`): `{ cancelled: false }`, `{ cancelled: true, branch: i }`, or `branch: null` when an enclosing `Parallel` cancelled it. A replay reproduces a cancellation rather than recomputing it: nothing cancels, each branch runs its recorded steps, a step missing from a branch the decision cancelled is where production stopped it (`fromTrace` throws the `replayCut` marker, and the interpreter stops that branch as cancelled), and the result is the recorded branch's failure. A `TimeParadox` fires if that branch no longer fails, or if the decision names a branch past the end. Nothing in a replay waits for a cancellation, so a diverged flow cannot hang. A branch whose own code threw is a trigger like a failing one; in a replay it throws again on its own, since its code runs again on the recorded results, and once the throw is fixed the crash trace replays as a `TimeParadox`. A negative branch, a trace without decisions, and a `Resolver` answering a `'Parallel'` step with anything but a decision all replay by timing. A `'Parallel'` step neither advances `index` nor reaches `onResolved`, `redact` never sees a decision, and a hook marks a cancelled `Parallel` from its decision, since `op` returns even when a branch threw.
- **A replay fault is a harness error.** `replayError` marks its errors with `harnessError`, so nothing that handles a domain failure (a Command's `next`, `onExhausted`, a settled `Parallel`'s outcomes) can absorb one; a truncated trace once replayed as a `Success` whose branches each carried the `ReplayError` as though production had returned it. `replayEffect` catches the fault at its own boundary and returns it as a `Failure`. A second mark, `replayFault`, tells it apart from an `EffectTypeError`, which keeps propagating, since a malformed flow is a bug in the flow rather than a problem with the trace. A new harness error gets the mark rather than a name to match on, since `TimeParadox` overrides the name `replayError` sets.
- **The outcome wrapper is load-bearing.** A `Resolver` returns `{ result }`, `{ error }`, or `undefined` for "not recorded", so a Command that returned `undefined` is distinct from a step with no recording, which is what makes `onMissing` trustworthy. A step a trace does not hold resolves to `undefined` just as it would from a `Resolver`, so `onMissing` applies to both; two things win over `'execute'`, a step recorded under another name, which is a `TimeParadox`, and a step a recorded cancellation explains, which production never ran. A trace whose `dropped` is above 0 refuses `'execute'` outright, before the replay starts, since the steps a cap drops are steps production ran: the README and the missing-step message once advised `'execute'` for exactly such a trace, and replaying a capped billing batch that way charged and invoiced it again. The message for a missing step names the case it may be, a step the cap dropped or one production never ran, because the fix differs. A bare entries array and a `Resolver` carry no `dropped`, so only the docs cover them. A trace entry marks a throw with `threw: true`, because JSON drops an `error` key whose value is `undefined`, as it is after a bare `reject()` or when `redact` removed the error, and that once turned a failed step into one that returned `undefined`. An `error` key without `threw`, as older and hand-written traces have, still reads as a throw.
- **Errors survive JSON.** `serializeError` carries `message`, `stack` when asked for, `cause` recursively, and an `AggregateError`'s non-enumerable `errors` under `__errors`, since that is where its detail lives; an enumerable `errors`, such as a validation error's, is data and is copied as it is. `reviveError` defines `name`, `message`, `cause` and `errors` as the original had them, so the README's check `assert.deepEqual(replayed, result)` holds for a `Failure` as well as a `Success`: non-enumerable, as on a native `Error`, unless `serializeError` listed them under `__enumerable`, which it does when one was assigned (`e.name = 'TimeoutError'`, or `e.cause = inner` from before the `cause` option). Such a key is not copied again with the other own keys, where a raw cause once replaced the serialized one and reached JSON as `{}`. A subclass revives as a plain `Error`, since the trace carries a name rather than a prototype, so that check holds for plain errors. A thrown value that is not an `Error` passes through unchanged. A `cause` or `errors` chain that loops back is cut where it returns, carrying that error's name and message only; following it overflowed the stack, and `observeSteps` dropped the step with the recorder's other failures, so the trace silently lacked it. Only an error's ancestors cut the chain, so one that appears twice without a loop is carried in full both times.
- **Recorded values are copies, both ways.** `snapshot` copies with `structuredClone`, or a JSON round trip without it, and when that throws, `copyAround` rebuilds arrays and plain objects and keeps only the parts that cannot be copied, such as a function or a logger, as they are; it does not fall back to JSON, which would drop those functions even in memory. Without a copy, a later step that mutates a returned object rewrites what the trace says an earlier step returned. `redact` is handed the copy, so a redact that deletes a field in place never reaches the run (one written as `delete value.password` once saved users without a password, but only while recording was installed), and what it returns is not copied again. Replay copies on the way out, in `entryToOutcome`, so a replayed step or a caller that mutates a value cannot change the next replay. The trace's own `initialInput` and `context` are copied when the run starts: `toTrace` copies what it is given at the moment it is called, so `recordEffect` calls it before the run, and so does the reference wiring, since an ORM save that assigns an id to the object it is handed otherwise rewrote what the trace said production received.

**`redact` sees everything a trace holds**: results, serialized errors, and the trace's own `initialInput` and `context`, told apart by its `kind` argument. Keep that coverage complete if the trace format grows a field, since a field `redact` cannot see is a field that leaks. An absent `initialInput` or `context` stays `undefined`, so a redact that spreads its argument cannot invent an empty object.

**What replay proves.** A replay checks that the flow still asks for the same Commands in the same order and still handles the same answers. It cannot check what the flow computes, since every result comes from the recording: fix the arithmetic in a pure step, replay the run that got it wrong, and the replay reports the old outcome as the fixed flow's answer, with nothing to flag. Test a value change against the pure step that computes it. `unreached` exists because a flow that stops issuing Commands early mismatches nothing, and the recorded steps it never asked for are the only evidence. It proves a step went away only when that step was the last one reached, since removing one from the middle shifts every later path and stops the replay at a `TimeParadox`. It rides beside the result rather than on it, so the outcome stays what production returned; it is a return value rather than an observer option, since a value handed to a callback once after completion is a return value in disguise; and it is absent rather than empty for a `Resolver`, which cannot know what it lacks. A regression test for a fix that skips a step asserts which step; every other recording asserts the list is empty.

**Observing a replay.** `onResolved` is the seam for observing a replay (logging, counting, step assertions), and a `Resolver` is the seam for supplying outcomes; narration that reaches for a `Resolver` is using the wrong one. A throw from `onResolved` stops the replay, and `replayEffect` rejects with the observer's own error, carried through a harness-marked stand-in so nothing in the flow absorbs it. It is not dropped the way `observeSteps` drops a recorder's error, because step assertions are one of the things the seam is for, and a swallowed assertion is a test that cannot fail. `timeTravel` narrates through `onResolved` and returns the bare outcome, since narration is its job; it looks each step's timing up by path, or by position for a trace without paths, falls back to `String(v)` for a value `JSON.stringify` cannot print, such as a `BigInt` or a cycle, and skips its unreached warning after a `TimeParadox` or `ReplayError`, since the error already names where the flow diverged. It warns when a trace holds no `initialInput`, since it rebuilds the flow from it and a hook-based recorder finds one only on a flow `effectPipe` built.

### TypeScript

`index.d.ts` is written by hand, apart from `effectPipe`'s overloads, and three checks keep it matched to `index.js`: the `Declaration parity` test pins the two export lists to each other, `tsd` checks `test/types.test-d.ts`, and `tsc -p jsconfig.json` runs strict `checkJs` over `index.js`, `test/all.js`, `test/types.test-d.ts`, `examples/*.js` and `scripts/*.js`. `test/all.js` imports `../index.js`, which TypeScript resolves to `index.d.ts`, so the tests are checked as a strict consumer of the public types. The config is named `jsconfig.json` and is strict so that VS Code, which reads only `jsconfig.json` or `tsconfig.json` and checks JavaScript strictly by default, and the gate read one configuration; add any checked JavaScript in this repository to its `include` list.

The declarations support TypeScript 5.1 and later, and `npm run test:ts-minimum` compiles them and `test/types.test-d.ts` with 5.1. Plain `tsc` checks there that every `@ts-expect-error` still fires and that every `expectType` argument is assignable, but not that types are exact, which stays `tsd`'s job on the current TypeScript. 5.1 is the first version that treats a mapped type over the branches as an array, which `ParallelState` requires; the declarations once compiled on 4.7 by accident, and a change to `Parallel` broke them there with nothing to notice. Two features they would otherwise use arrive in 5.4, `NoInfer` and `const` type parameters that infer a tuple through an intersection, so `Parallel` works around both. Raising the minimum breaks users on the older compiler, so it goes in the changelog as a breaking change.

Deliberate type errors in `test/types.test-d.ts` are `// @ts-expect-error` directives, never `tsd`'s `expectError(...)`: `expectError` leaves a real diagnostic that `tsd` swallows and every other tool reports, so the file could not be part of the `tsc` gate and showed red in an editor. A directive reports `Unused '@ts-expect-error' directive` if the error stops occurring, and `tsd` fails on that, so the assertion is as strong. It is satisfied by any error on its one line, so keep each suppressed expression on one line and small enough that only the intended mistake can fail it, and give each a reason.

`Effect<T, E, Ctx>` carries the value, the error union and the context. Each `effectPipe` step has its own context type and the pipeline's is their intersection, because one shared `Ctx` was inferred as `unknown` whenever a step declared none, which switched context checking off for the whole pipeline; `unknown & AppCtx` is `AppCtx`, so a step that reads no context costs nothing. `runEffect` and `recordEffect` require the context when the flow's context type is not `unknown`, since the runtime would hand `Ask` an empty object. An error union survives without return annotations, since a step that cannot return a `Failure` contributes `never` (see below), and `Failure` takes a `const` type parameter, so a string passed to it keeps its literal type with no `as const`. The declared union leaves out what a Command's function throws, which `runEffect` returns as a `Failure` all the same, so the code handling a result needs one fallback, as the settled decision on thrown errors says.

`effectPipe` is 20 overloads, one per pipeline length, in one shape (values `T0` to `Tn`, then errors `E1` to `En`, then contexts `C1` to `Cn`), and two thirds of index.d.ts. `scripts/effect-pipe-overloads.js` writes them between two marker comments, formatted with the repository's Prettier configuration so `npm run format` leaves them alone, and a `Declaration parity` test fails when the file and the script's output differ. Change them in the script and run `npm run generate`, never by hand: a pattern meant for their type parameters once also rewrote ten return types. Their doc comment lives in the script too, since a marker between it and the first overload would detach it, and raising the ceiling is `MAX_STEPS`. Past 20 it is a compile error, and nesting is the workaround.

Declarations that exist for a reason, each pinned in the tsd file:

- `Retry`'s error is `E | RetryExhaustedError`. An abort escapes as its own `E`, and `lastError` is `unknown`, since only a thrown value reaches it and nothing declares what a function throws; the type parameter defaults to `unknown` for a caller who knows what their function throws, as `test/all.js` does with `RetryExhaustedError<Error>`. With `onExhausted` the error is `E | E2`, and that overload comes first. `RetryState`'s `effect` is typed `Effect<T, any, Ctx>`, since the node declares its own error.
- Every state's `next` is a method signature rather than a function-typed property. Under `strictFunctionTypes` a property's parameter is checked contravariantly, so a Command whose function only throws, a `CommandState<never, ...>`, was not assignable to `Effect`; method parameters are bivariant.
- The non-settled `Parallel` overloads accept only `settled?: false`, since a `settled` known only as a `boolean` matched the overload that types `next` as values while the runtime handed it outcomes. An options variable used only for its `limit` is typed `{ limit: number }`.
- `Command` ends with an overload that keeps the defaults of 0.15: `R` for the value and `unknown` for the error. Given some type arguments, TypeScript infers none of the rest, so they take their defaults, and the `never` defaults refused `Command<User | null>(fetchJson, (u) => (u ? Success(u) : Failure('not_found')))`, the usual way to type a JSON response, which had compiled. A call with no type arguments matches an exact overload first and keeps its exact types, which is why the fallback comes last. `Ask` and `Retry` have none, deliberately: partial type arguments are rare there, and the extra overload turned the two-line error for their commonest mistake, a callback returning a plain value, into a report on every overload, so there a step that can fail needs every type argument or none. `Parallel` has none either, since its type parameter is now the branches, and `effectPipe` never accepted partial type arguments. The README recommends writing the Command function's result type instead, which keeps every other type inferred.
- `Failure`'s type parameter is `const`, so a string error keeps its literal type and an inferred union needs no `as const`, which the experiments otherwise wrote on every error string. It makes an object error readonly with literal properties, still assignable to a mutable type, and an array error a readonly tuple, which a mutable array does not accept. `Success` has no `const`, since a literal or readonly value would narrow what later steps receive.
- `Command` has a first overload for the default `next`, since without it a `Command(fn)` inside an annotated step inferred its value as `unknown`, and `Retry(Command(fn))` failed to compile in the shape the README recommends.
- Every type parameter that takes an error from what a function returns (`Command`'s, `Ask`'s, `Retry`'s, and `effectPipe`'s `E1` to `En`) defaults to `never`, so a step that cannot return a `Failure`, such as a Command with the default `next` or a pure step that only succeeds, adds nothing to the union. They defaulted to `unknown`, which absorbs every other member, so the Quick Start written in TypeScript reported `error: unknown` because its `saveUser` passes its result straight through. The value parameters inferred the same way (`Command`'s `T` with an explicit `next`, `Ask`'s `T`, `Parallel`'s `R`, and `effectPipe`'s `T1` to `Tn`) default to `never` for the mirror reason: a `next` that can only fail adds nothing to the value. They were `unknown`, or for `Command` the function's result, so a step that either succeeded or compensated and then failed, `ok ? Success(order) : Command(refund, () => Failure('declined'))`, did not compile in a pipeline, which the checkout experiment found. The type aliases keep `unknown`, since an annotation such as `Effect<User>` that leaves the error out means any error.
- `CommandInterceptor` is a union of an async and a plain function type, since in JavaScript a JSDoc `@type` on an async function must declare a `Promise` return. `StepRunner`'s `path` and `onRun`'s `flowName` are declared present, since the runtime always passes them.
- `redact`'s value is `any`, since every redact spreads or reads it. `version` accepts `undefined` explicitly for `exactOptionalPropertyTypes`, which `tsd` does not run with, so that one was checked by hand and is not pinned.
- `Parallel` reads each branch's value, error and context from the branch itself, through `ParallelValues`, `EffectError` and `ParallelContext`, which combines branch contexts the way `effectPipe` combines its steps'. The branches were once typed with one shared error and context that nothing inferred, so both were `unknown`: every `Parallel` read as needing no context, so a branch reading `AppCtx` let `runEffect` run with none and `Ask` got `{}`, and every pipeline holding a `Parallel`, including every loop the README teaches, lost its error union. Three details of the declaration each close an `any` leak or keep TypeScript 5.1 working. The branches are checked by `ParallelBranches`, a conditional, rather than by a constraint, since a constraint such as `readonly Effect<any, any, any>[]` is also the contextual type of each branch, and an `Ask` or `Retry` written inside the array took `any` from it. `B extends readonly unknown[] | []` infers an array literal as a tuple, since a `const` type parameter does so through `ParallelBranches`' intersection only from TypeScript 5.4; before that the branches collapsed into one array type and the `any` leaks came back. And `next`'s error appears in the non-settled return type as `[E][E extends any ? 0 : never]`, which is `E` once resolved but offers nothing to infer from, because a bare `E` in a union with the branches' error was also inferred from the expected return type, and inside `effectPipe`'s arguments that came out as `any`; a defaulted type parameter for the branches' error leaked the same way and let a too-narrow annotation compile. Under `settled` the node's error is `next`'s alone, since a branch's failure reaches `next` as an outcome, and `ParallelState`'s sixth parameter, `BranchError`, types `effects` with the branches' errors; `Effect`'s `Parallel` member takes `any` there so a settled node stays assignable. `ParallelOutcomes` takes the branches, so each outcome carries its own branch's error. `EffectValue`, `EffectError` and `EffectContext` are named for general use because every type in a `.d.ts` module is public whether or not it says `export`.

The tsd file also covers the recording and replay types and `CallConfiguration`'s boolean `inherit`; extend it when touching those types.

### Reference integrations

`examples/opentelemetry-example.js` and `examples/recording-example.js` are reference code, not part of the library, and both have suites, so edit them only with `npm test`. Each exports a function that returns a configuration (`telemetryHooks`, `recordingHooks`), which is the form that composes, and one that installs it (`enableTelemetry`, `enableRecording`); nothing happens on import. The rule for both is that observing a run never decides it.

- **Telemetry** opens a span per run in `onRun`, a child span per Command in `onStep`, and one per `Parallel` around its branches' spans. Spans carry names, timings and status, never values: values belong in a trace, where `redact` strips them and a replay can use them, whereas a span attribute can be redacted neither afterwards nor before a password in an input reaches the backend. `onStep` must `await op()` and return its result, and nothing ahead of the run may throw, since serializing a cyclic input there once left flows unexecuted.
- **Recording** keeps one recorder per run in an `AsyncLocalStorage` scope: `onRun` packages the input before the run, the first `onBeforeCommand` copies the context, and `onStep` passes `path` on. An error from `keep` or the sink goes to `onSinkError`, by default `console.error`, rather than replacing the run's outcome. The first kept trace of a flow that carries no input produces a warning through `onWarning`, by default `console.warn`, once per flow, since that trace cannot rebuild its flow and the time to find out is before an incident. A kept trace that `maxEntries` cut short produces its own warning, once per flow, since it replays only up to the first step it lacks, and the default cap of 500 cuts a long batch run short without anyone having chosen to. A run that rejects because its own code threw is offered to `keep` as a `Failure` and sent to the sink before the rejection is rethrown, since those are the runs most worth replaying; `recordEffect` rejects without its trace, since in a test or a script the error is already in front of the caller.

## Settled decisions

Each of these was weighed and decided. Do not propose them again as improvements or rank them as weaknesses; the reasons are here.

- **No generator syntax.** A generator-based flow would yield the same Command objects, but a generator is used up as it runs, while a flow built from Commands and `next` continuations is a reusable value: a test calls `step.next(null)` and `step.next({ id: 1 })` on the same node to explore both branches, `chain` wraps a sub-pipeline it did not build, and the `Kleisli laws` suite holds because continuations compose. Neither form lets a reader see past the next Command without supplying an answer, so inspection is not the difference; reusability is. The nesting that dependent values cost is the price, and the `Composing Larger Flows` patterns keep it low.
- **No catch.** An `Attempt` node was designed and rejected: catch brings non-local control flow into a design whose point is explicit data flow, and every motivating case but one was already expressible, as the README's `Which Errors Are Data` section shows (an outcome the flow handles is data that a `next` branches on, and `Failure` means abort). The exception, recovering from `Retry` exhaustion inside the flow, became `Retry`'s per-use `onExhausted`, for three reasons: it had no in-library expression, since the workaround split one operation across two runs and two traces; retry-then-fallback is a standard resilience pairing (Polly, resilience4j), so the demand was predictable; and it completes `Retry`'s own failure handling rather than adding catch. The ceiling stands: no general catch, only an I/O fault is recoverable (from anywhere in the wrapped tree, deliberately), `onExhausted` is per-use, and a cancelled branch skips it.
- **`attempts: 0` throws.** A `Retry` that does not retry is not a `Retry`, and `0` was the one spelling that made `onExhausted` a catch at no cost. `attempts: 1` still recovers from any I/O fault, but at the visible cost of running the tree twice. A companion option was dropped for the same reason, since `settled` already isolates a batch branch.
- **No global retry options.** How a dependency misbehaves is a property of that dependency, not of the process, and a shared `const flakyNetwork = { attempts: 3, backoff: 2 }` passed to each `Retry` covers the repeated case where anyone reading the flow can see it. A `retry` key throws rather than being ignored, since ignoring it would quietly turn a configured `attempts: 5` back into 3.
- **`settled` hands `next` `Success` and `Failure` nodes**, not `Promise.allSettled`'s `{ status, value }`, since the library already has a vocabulary for succeeded or failed. It exists because a batch of independent records was the one shape nothing could express: one bad record cancelled the rest mid-flow, which in a billing job meant a charge with no invoice.
- **A `Parallel`'s trigger is the first failure to finish**, not the first by array order. Either is a true answer, and a replay returns the recorded one. The docs once promised array order and were corrected rather than the code.
- **No `AbortSignal` for a whole run**, and none reaches a Command outside a `Parallel`: most flows are a few quick Commands, and a caller that needs one puts a signal in the context. A signal read that way makes the function throw, which is an I/O fault, so a `Retry` around it retries and then runs `onExhausted`, and the run can report the fallback's `Success` after the caller cancelled; inside a `Parallel` the interpreter checks its own signal and skips both.
- **No finalizer inside a flow.** Cleanup for a run, a transaction included, is a try/finally around `runEffect` in the shell.
- **Recursing through `effectPipe` is quadratic, and that is left alone.** `poll = (n) => effectPipe(fetch, (s) => (s.done ? Success(s) : poll(n - 1)))(n)` wraps one more continuation per level and overflowed the stack at 20,000 levels; the same loop recursing through a Command's `next` stays linear. Loops that long are rare, so a docs note that loops go through `next` is the most it warrants.
- **Nested pipelines for dependent values are a TypeScript cost only.** In JavaScript a step can close over anything in scope; threading the value is what keeps a typed pipeline checked.
- **No join helper.** `pair(f)`, a step passing on `[value, result]`, was built, tested and dropped. It was exactly the local join `(value) => effectPipe(f, (result) => Success([value, result]))(value)`, and strict TypeScript inferred its parameter, but it traded field names for positions, so two values of one type could swap without a compile error, and chained pairs carried everything forward, an accumulator with no names. Avoiding both took a reshaping step after each pair, at which point it was no shorter than the local join. An optional argument to shape its output was rejected as well, since `pair` would then not return a pair. The awkward part of the local join, an argument trailing far from its function, is answered by naming the join as a step, as the README's `withCustomer` does, and a lookup written in place joins in its Command's own `next`. A builder that accumulates named results (`bind`, as fp-ts and Effect-TS do it) is the accumulator the README warns against, and direct style written as an async function with `await run(name, fn)` steps gives up the guarantee that a replay does no I/O, since a stray `await` would run for real.
- **No flows written as one function.** `flow(fn)`, where a synchronous `fn(input, run)` got each step's value back from `run`, was built as a spike and dropped. It produced ordinary trees: `run` threw a marker at the first step without an answer, and that step's `next` ran the function again from the top with one more answer, so a flow stayed a reusable value, shared traces with the continuation style, and a `Retry` handed to `run` wrapped only its own tree. It was dropped because its syntax hides how it runs. Code that reads as running once, in order, ran once per step, so it needed guards against the habits it invites (a decision that changes between runs, a `try`/`catch` around `run`, an `async` function, a `run` after returning), and copies of every answer on every run, which took a 5,000-step loop of object answers to 7.8 s against about 1 ms through `next`. It lost the error union in TypeScript, hid the data a flow is, which is what the README teaches, and left two styles for the docs to carry. Newcomers from `async`/`await` get the README's `Coming from async/await` section instead, which maps what they would write to the flow that does the same.
- **No loop helper; a loop is taught as two parts.** `Loop(start, pass)`, whose pass returned `Again(state)` to go round again or took a separate `while` condition, was proposed and dropped before it was built. It removed the self-call from a loop whose passes need each other's answers, but it read no more like the loop a newcomer from `async`/`await` would write than the recursion it replaced, and `Again` would have been a seventh node type for `chain` and the interpreter to carry. The README splits a loop the way its `async` version is usually written: a step that gets the list, then `Parallel(list.map(f), { limit: 1 })`. When getting the list is itself a loop, as with cursor paging, that loop stays an ordinary `async` function called from one Command, which keeps the Command's function a single call; the README states the cost (one trace step holding the whole list, a `Retry` that starts again from the first page, and a loop no flow test can see). Recursion through a Command's `next` gets one sentence, for a loop that has to decide something on each pass, and the recursive paging example was dropped, since recursion is the hardest thing in a flow to follow.
- **A `TimeParadox` after a flow changes shape is the design.** A trace belongs to the version of the flow that recorded it, nothing resumes a recorded run against newer code, and matching loose enough to survive an inserted step would have to guess. An incident test is re-recorded when its flow changes shape.
- **A trace records results, never Command arguments.** Given `initialInput` and the recorded results the flow runs the same way again, so replaying to a step rebuilds its arguments. A guardrail vetoes on the context or on `meta`, which `onBeforeCommand` receives; a cache hook would need `meta` handed to `onStep`, not recorded arguments, and nothing has needed one. Recording arguments would double a trace's PII surface for no replay benefit, since arguments are usually the sensitive half of a call.
- **A trace keeps data, not objects.** `structuredClone` drops classes and a JSON sink loses more, such as `Date` and `Map`. Keeping references to class instances brings back the mutation bug for the values most often mutated, ORM entities, and cannot survive JSON anyway; a tagged value encoding with per-class codecs is more machinery than the problem warrants. Commands return plain data instead, as the README says.
- **Steps match by path, with no option to choose.** A `strict` option once chose between positional matching and a per-name queue, and the queue was the bug paths fixed: it paired a step with the next entry of the same name, which is completion order, so two `Parallel` branches calling one Command swapped results whenever the replay finished in a different order. It was removed rather than left as a trap; a `Resolver` matches by any other rule. Marking each step that finished after its branch was cancelled was rejected too: it fixes one case and leaves a branch stopped between steps with no step to mark.
- **`fastRetry` is a parameter of the interpreter**, not a rewrite of the tree. `zeroRetryDelays` rewrote the tree into copies with `delay: 0`, which was replay walking the tree itself: it had to mirror the interpreter's node types, and a type it missed would have replayed a slightly different flow with nothing to flag it. The interpreter already knows it may be replaying, since it reproduces recorded decisions and stops branches at a replay cut, so the flag adds a setting rather than a kind of knowledge. It lives on the private `interpret`, not on `runEffect`'s `callConfig` or as a fourth argument, so no public function carries a setting only a replay should use.
- **Per-call configuration merges; it never replaces one slot.** `inherit` is a boolean: merge over the installed wiring by default, over nothing when `false`. Replacing a single slot was dropped because it caused a real bug (`recordEffect` inside an instrumented application produced runs with no spans), because it means something only when you know what the other slots hold, and because nothing but replay needed it. The name was chosen over `global`, Node's alias for `globalThis`, and `ambient`, a new noun. `configureEffect`'s layers replaced a one-slot rule under which a later install displaced the earlier wiring and a late restore could discard another caller's hooks.
- **What is internal stays internal.** `fromTrace` is not exported: a caller with traces in another shape writes a `Resolver`, and one who only wants to watch uses `onResolved`; export it again if rewriting outcomes from a reference trace comes up, since `onResolved`'s return value is ignored. `observeSteps` was briefly exported as `observe` and removed, since it cost 270 bytes for one internal caller and no consumer, the same argument that removed `tap`. `chainHooks` was briefly exported and folded into `configureEffect`, since a merge is only useful on the way into a configuration.
- **The conveniences stay.** `recordEffect` and `timeTravel` own the trace metadata. `timeTravel` could be rebuilt from `onResolved` in ten lines, but the one-line form is what makes the feature graspable.
- **Recording stays out of the library.** `node:async_hooks` would be `index.js`'s only import, and a Node-only one, and the policy the reference wiring encodes (what to keep, where the sink is, what `redact` strips) belongs to the application.
- **`effectPipe` stops at 20 steps.** A single variadic signature built from recursive types loses the parameter type an unannotated inline step infers from the step before, and its errors are far harder to read; a catch-all overload past 20 would silently stop checking a long pipeline while it looked typed. A compile error at 21, with nesting as the workaround, is the honest failure.
- **`index.js` stays one file.** Splitting it by concern would mean going back and forth between files to follow one path, such as a Command from the interpreter through a hook into the recorder, which costs a reader more than a long file does.
- **`runBranches` runs both modes through `settleBranches`.** It once held two algorithms, running live and reproducing a recorded cancellation, with a `reproducing` flag checked in three places. Now `settleBranches` takes the one thing the modes differ in, the rule for whether a settled branch cancels the others, and `runBranches` reads the mode in two places a few lines apart. Splitting the modes into `decideByTiming` and `reproduceCancellation` was tried and folded back: following one `Parallel` went through seven functions, with the same four arguments handed down unchanged.
- **Thrown errors stay out of the declared error union.** A `Failure` can also carry what a Command's function threw, what an `onBeforeCommand` veto threw, or, in a replay, a `ReplayError` or `TimeParadox`, and the types name none of them. Declaring results as `FailureState<E | Error>` was weighed and dropped: an application handles the `Failure`s its steps return, a Command's function catches what the flow can handle and returns it as data, the rest is left to throw so `Retry` can act on it, and whatever reaches the caller undeclared needs one fallback where the result is handled, not one per Command. Widening every result type would make every handler spell out a case it treats generically anyway. The README says to write that fallback and to treat it as a server error, and its checkout handler answers a thrown error with a 500 rather than a 400.
- **Sharp edges are documented, not guarded.** `Retry` repeating its whole wrapped tree, a `Parallel` branch whose Command ignores its signal running to completion, and a function passed by name taking the signal for an optional first parameter are pinned by the `Documented sharp edges` suite and each has a README Limitations entry; a guard would have to ban legitimate trees, since the hazard is not visible in the data. Replay's refusal of `onMissing: 'execute'` on a capped trace is consistent with this: the trace records its own cap, so that guard bans nothing legitimate. If `Retry` is ever changed to resume rather than repeat, that suite is the one to read first.

## Tests

`test/all.js` holds every runtime test, with a user-registration domain as the running example. `registerUserFlow` has the same shape as the README's Quick Start, so the tests and the documentation demonstrate one idiom. The test names say what each suite covers; these are the conventions they follow.

- **Assert on the returned data**, such as Commands, Failures and traces, rather than on side effects. That is the usage pattern the library exists for.
- **Reset the hooks in every suite** with `beforeEach(() => configureEffect())`, a bare call. Hooks are process-wide and outlive a suite, and `configureEffect({})` adds an empty layer rather than resetting: suites guarded that way once ran under whatever the previous suite had installed, and stayed green only because the leaked hooks wrote to arrays nobody read. The first suite resets too, since being declared first is luck rather than isolation.
- **Count I/O in replay tests.** Their Commands count their own invocations, so a test can assert that a replay performed none, and a replay is checked from memory and from JSON.
- **Test behaviour through the public surface.** Composition such as `configureEffect merging` and `Per-call inherit` is checked by what runs rather than by inspecting a merged object, and an internal such as `observeSteps` is reached through its only public consumer.
- **Anchor an equation to a value.** The `Kleisli laws` suite checks the laws by running both sides, and since a `chain` that dropped every continuation would satisfy them with both sides equally broken, it also anchors one composition to the value and I/O computed by hand.
- **Each example file has a suite**, so a change to the hook contract breaks the examples rather than letting them rot. The telemetry suite injects a stub through the example's `tracer` option, which is why that option exists.
- **Audit the guidance when behaviour changes.** Write the flow a careful reader would write after reading each documented sharp edge, and run it: twice the code here moved and the README's advice did not move with it.

`test/types.test-d.ts` holds the type-level tests, run by `tsd`; its deliberate errors are `@ts-expect-error` directives, for the reason under TypeScript.

### README examples

README snippets are code readers copy, and the `README examples` suite runs them: every `js` block is extracted and executed as one program, with the Quick Start's definitions in scope, each block seeing what the blocks above it in its section defined, and everything outside the library stubbed, so every `assert` the README prints is live. Each block's scope sits inside the previous one's rather than sharing it, since two independent examples in one section both declare `result`. Node's `node:test` mocks are the exception to stubbing: `Coming from async/await` sets a mocked test of the `async` version beside the flow's test of the same branch, because the code alone is the comparison `async`/`await` wins and the tests are where the small functions pay off, and the mocked test should pass against that function as it would for a reader. It also checks that blocks are found at all, since a regex that stopped matching would turn every check into a pass over nothing, that each block parses, and that every name imported from `'pure-effect'` is exported. So a fenced `js` block must be real JavaScript: a value shape goes in a `text` block and a placeholder is written out rather than `...`. A `ts` block is not run: the `command` helper in `Testing Without Mocks` was compiled and run by hand against a TypeScript version of the Quick Start, so check it the same way when the types it touches change. A block that reaches for something new outside the library needs a stub in that suite. The suite exists because wrong examples kept surviving review by looking right, and it was verified against the two that actually shipped wrong.

A tree walk checks which Command comes next; a step's `next` is where the piped value can be seen, so `assert.deepEqual(ensureEmailAvailable(input).next(null), Success(input))` is what catches a guard that resolves to `Success(true)`, which a walk misses. The one thing that cannot be asserted on is the body of a Command's function, since reading the values it closes over means calling it, so keep those bodies to a single call. Two shape rules keep documented pipelines honest, and the Quick Start follows both:

- **Every step accepts and returns the piped value.** The email guard's `next` returns `Success(input)` rather than `Success(true)`, so `saveUser` receives the registration data; a guard that is already a Command threads the value at no cost, which is why no combinator is needed for it.
- **Prefer threading the value over `() => f(outer)`, without presenting it as a rule.** Closing over an outer variable works in JavaScript, and the README says so. The cost is TypeScript's: a step that ignores its parameter constrains nothing about what produced it, so a changed upstream type raises no error. JavaScript examples have no type check at all, which is how the `Success(true)` bug shipped; the equivalent TypeScript is rejected with `'boolean' is not assignable to 'User'`.
