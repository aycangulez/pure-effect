# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm test                                          # run all tests
npx mocha test/all.js --grep "pattern"            # run a single test by name
npm run format                                    # Prettier over index.js, index.d.ts, examples/*.js, test/all.js, test/types.test-d.ts, README.md, CLAUDE.md, CHANGELOG.md, CONTRIBUTING.md
npx tsd                                           # type-level gate over test/types.test-d.ts
npx tsc -p jsconfig.json                          # strict tsc over index.js, test/all.js, test/types.test-d.ts, and examples/*.js, reading index.d.ts as a consumer; the same config VS Code uses
npx esbuild index.js --minify --format=esm | gzip -9 | wc -c    # the size the README claims
npx stryker run                                   # mutation testing: mutates index.js, runs test/all.js against each mutant; report in reports/mutation/
```

No build or lint step: the library ships as plain ES modules with no transpilation. Formatting is Prettier, configured in `.prettierrc`; match it when editing. `.github/workflows/ci.yml` runs `npm test` on Node 18 through 24 and, in a second job, Prettier's check; it triggers on pull requests and on pushes to `main`, not on a bare branch push. The size measurement, the two grep rules below, and mutation testing stay manual. Mutation testing is configured in `stryker.config.json` and needs Node 22 or later, which is why it is not in CI, whose matrix starts at 18; on Node 18 and 20 `npm ci` only warns about its engine. A test that passes whatever the code does is invisible to every other check here: three such tests were found by reading, and a mutation run is how the rest are found, so run it after changing `index.js` or its tests. Its survivors are not a to-do list. Most are equivalent mutants that change nothing observable (optional chaining on an `AbortController` that always exists, arrays pre-sized and then filled, `performance.now()` against `Date.now()`, `chain` cases that fall through into identical code, the check after a retry backoff that the loop's own check repeats) or message and narration wording. Two gaps are left on purpose: whether each nested `Parallel` removes its listener from the enclosing signal, which only an internal inspection could test, and the exact wording of `timeTravel`'s narration. A survivor outside those classes is a behaviour no test pins, which is what the run is for. `package.json` has a `files` list, so anything new that must ship in the tarball has to be added there; `npm pack --dry-run` shows what would be published. `CONTRIBUTING.md` restates the rules in this section for a human contributor and points here for the reasons; a new rule goes in both, a new reason only here.

The README's size badge is live: `img.shields.io/bundlejs/size/pure-effect` measures the latest published version with esbuild, the same tool as the command above, so it corrects itself within hours of a publish and reads the previous release's size until then. Bundlephobia's badge was not used because it measures with webpack and terser, so its number differs from the local one, and its Shields integration is often rate limited. The feature bullet also states the size in prose, and that sentence cannot correct itself: re-measure with the command above after adding anything to `index.js` and reword it when the number moves. That bullet is the only place the size is written down. **A commit message and a changelog entry never mention it.** Both are read long after the fact, when the number they quote is stale and the reader has no way to tell; the README bullet is the one copy that gets re-measured, and a second copy in a record nobody re-measures is a copy that goes wrong quietly. Size is also not what either document is for: a changelog answers what changed for a user and a commit message answers why, and neither question is answered by a byte count. Measure it, update the bullet, and leave it out of the history.

**Markdown prose has no hard line breaks.** Write each paragraph and each list item as one line and let the editor soft-wrap; never wrap prose at a column. Hard breaks make later edits reflow whole paragraphs, turning a one-word change into a multi-line diff. `proseWrap: never` enforces this, so `npm run format` unwraps any prose that arrives wrapped. Even so, write it unwrapped in the first place rather than relying on the sweep, since a wrapped paragraph reads as an intended shape until something reflows it. Fenced code blocks are untouched by the setting, and table rows stay one per line; only prose joins.

**No jargon in the README.** A reader meets the library there and should never need vocabulary from functional programming, from the interpreter's internals, or from this file to follow it. What the library exports is not jargon: `Command`, `Retry`, `Parallel`, `Resolver`, `TimeParadox`, `onStep`, `backoff` and the rest are what the things are called, and a reader has to learn them anyway. Everything else gets the plain word. A flow, not an Effect tree. Part of a flow, not a node or a subtree. The Command's function, or `cmd`, not a thunk. Joining, not fan-in. Stops, not short-circuits. A request, not cooperative. Attached, not stamped. Does the same thing again, not deterministic. No catch, not no catch combinator. Runs at the same time, not concurrently, wherever nothing turns on the distinction. `grep -rniE "thunk|combinator|monad|kleisli|effect tree|fan-in|fan-out|short-circuit|cooperative|imperative shell|arity|stamp" README.md` checks a change before it lands and should print nothing. This replaced a rule that banned `thunk` alone, which was the same instinct applied to one word: every other term on that list had already reached the README, and `Independent fan-in` was a section heading. A precise term a reader genuinely benefits from may stay if the plain words follow it in the same breath, which is why `idempotent (safe to run more than once)` survives in the Retry section and is not on the grep list: the gloss is what makes it a definition rather than a gate. That is the exception, not a way around the rule, and a term that needs a gloss every time it appears is a term the README should not be using. The precise words stay available everywhere else, in this file, in JSDoc, in code comments, and in test names, where the reader is a maintainer and precision is worth more than approachability.

**No em dashes.** The `—` character does not appear anywhere in this repository: not in `README.md`, not in this file, not in JSDoc, code comments, test names, or assertion messages. Reach for the punctuation that carries the actual relationship instead of a dash that blurs it. A colon when the second half explains or names the first. Parentheses for an aside the sentence could survive without. A semicolon between two linked independent clauses. A comma for a light pause or a trailing "which" clause. A full stop when the clause can stand on its own, which is usually the honest fix for a dash joining two complete thoughts. Nothing enforces this mechanically, so it is on the author; `grep -rn "—" --include="*.js" --include="*.ts" --include="*.md" .` checks a change before it lands. Table cells that need a "not applicable" placeholder use `n/a`.

## Architecture

**pure-effect** is a zero-dependency effect system for JavaScript implementing the "Functional Core, Imperative Shell" pattern. Business logic returns plain data structures instead of executing side effects, enabling testing without mocks. The same property makes runs recordable and replayable: because a flow is inert data until the interpreter walks it, a recorded run can be fed back through the interpreter with no I/O at all.

### Core abstractions (all in `index.js`)

| Export | Shape | Purpose |
| --- | --- | --- |
| `Success(value)` | `{ type: 'Success', value }` | Wraps a successful result |
| `Failure(error, initialInput)` | `{ type: 'Failure', error, initialInput }` | Short-circuits the pipeline |
| `Command(cmdFn, nextFn, meta)` | `{ type: 'Command', cmd, next, meta }` | Defers a side effect for the interpreter; `meta.name` sets the Command's identity |
| `Ask(nextFn)` | `{ type: 'Ask', next }` | Reads the `context` passed to `runEffect`; passes it to `nextFn` |
| `Retry(effect, options)` | `{ type: 'Retry', effect, options, next }` | Wraps any Effect tree with retry-on-failure semantics; handled natively by the interpreter; a per-use `options.onExhausted` runs a fallback Effect when every attempt has failed |
| `Parallel(effects, next?, options?)` | `{ type: 'Parallel', effects, next, options }` | Runs multiple Effect trees concurrently; the first branch to fail cancels its siblings and its Failure is returned; context flows into all branches |
| `effectPipe(...fns)` | n/a | Composes functions into a sequential pipeline via `chain` |
| `runEffect(effect, context, callConfig?)` | async | Interpreter: traverses the effect tree, executes Commands; resolves `Ask`, `Retry`, and `Parallel`; a per-call `callConfig` merges over the configured hooks, or replaces them under `inherit: false` |
| `configureEffect(...configs)` | n/a | Adds a layer of process-wide telemetry hooks (`onStep`, `onRun`, `onBeforeCommand`); layers merge, earliest outermost; returns a function that removes the layer; a per-call `callConfig` merges over the result |

The recording and replay exports are a 2x2 rather than four loose helpers: `recorder` and `replayEffect` are the capabilities, at the hook and tree level, while `recordEffect` and `timeTravel` are the flow-level pair that also own trace metadata. That metadata is why the conveniences exist and should not be cut as mere sugar: `initialInput` lets a flow be rebuilt, `context` lets `Ask` resolve on replay, and `version` makes a stale trace detectable. A caller who assembles a trace by hand and forgets `context` gets one that silently diverges. `timeTravel` is presentation over `replayEffect` and could be rebuilt from `onResolved` in about ten lines, but it stays: the one-line form is what makes the feature graspable.

`Command(cmd, next, meta)` keeps that parameter list, and `next` is optional because most of Commands in this repo pass their result straight through: it defaults to `(result) => Success(result)`. `Parallel`'s `next` follows the same convention, defaulting to `(values) => Success(values)`, so a bare `Parallel(effects)` resolves to the ordered array of success values. The README's `Composing Larger Flows` section documents the composition patterns the primitives already support (sub-pipeline branching, `Parallel` fan-in, local joins that carry a minimal purpose-shaped value); those shapes need no combinators, which is why none were added. The no-accumulator guidance there is deliberate bug avoidance, not taste: a growing scope object hides which step depends on what, lets stale fields outlive their producers, and widens what carries PII, so keep the section's examples threading minimal values if they are ever reworked.

There is deliberately no generator syntax, and it should not be proposed again as the answer to the nesting that dependent values cost. A generator-based flow would yield the same Command objects, so it looks like a free front end over the same tree, but it breaks logic as data where it matters: a flow built from Commands and `next` continuations is a reusable value, and a generator is used up as it runs. A test can call `step1.next(null)` and `step1.next({ id: 1 })` on the same node to explore both branches; `zeroRetryDelays` rewrites a whole tree through its continuations and `chain` wraps a sub-pipeline it did not build, neither of which can reach inside a running generator; and the `Kleisli laws` suite holds because continuations are plain values that compose. Neither form lets a reader see past the next Command without supplying an answer, since `next` is a closure too, so inspection is not the difference; reusability is. The nesting is the price of the design, and the way to keep it low is the `Composing Larger Flows` patterns: sub-pipelines and small local joins.

There is deliberately no catch combinator (an `Attempt` node was designed and rejected), and the README's `Which Errors Are Data` section is the guidance that replaced it: an outcome the flow handles is data (a `next` branches on the result, and a rejecting `cmd` function catches into a result shape at the boundary), while `Failure` means abort and is reserved for the shell. Fallbacks written this way are fully traced and replayed; the failed attempt is recorded as that Command's result with the error as data, so nothing is lost, only categorized as handled. Catch was rejected because it reintroduces non-local control flow into a paradigm whose point is explicit data flow, and because every motivating case except one was already expressible. The one exception, recovering from `Retry` exhaustion in-flow, is now covered by the scoped per-use option `Retry(effect, { onExhausted })`. It was added, where general catch was rejected, for three reasons worth keeping: it was the only composition with no in-library expression (the shell workaround split one logical operation across two runs and two traces); retry-then-fallback is a canonical resilience pairing (Polly, resilience4j), so demand was predictable rather than speculative; and it completes `Retry`'s own failure handling rather than adding catch semantics, since `Retry` was already the node that reacts to failures and previously abdicated on the last one. The ceiling stands: no general catch node, nothing but exhaustion is catchable, `onExhausted` is per-use only (there is no configured `retry` for one to live in, and the tsd file pins that `configureEffect` refuses the key), and a cancelled branch skips the fallback.

A Command's identity is resolved by the internal `commandName(eff)`: a non-empty string `meta.name`, else `cmd.name`, else `'anonymous'`. That identity is used in three places at once, which is why it has its own function rather than being inlined at the call site: trace entries are keyed on it, replay matching compares it against the recorded name, and telemetry spans are titled with it. `meta.name` exists because the previous rule, `cmd.name` alone, made the flagship feature depend on syntax: an inline arrow silently recorded as `'anonymous'`, and any minifier that mangles function names renamed every step of every trace. Both failures are silent, which is the worst property an identity can have. `cmd.name` remains supported and is what the examples use, since naming the thunk reads well and needs no second argument.

Anything that is not an Effect is rejected by `asEffect` / `effectTypeError` with a message naming its source, and the distinction they encode is deliberate: a malformed flow is a bug and throws, while a Command that rejects is a domain outcome and becomes a `Failure`. The interpreter's catch rethrows `EffectTypeError` specifically so a flow bug cannot masquerade as a business error. Two details are important. `chain` validates the return of each pipeline step, which is the only place the offending step's name is known (`fn.name`), so that is where the useful message comes from. And the interpreter's `while` condition guards on `eff &&` before reading `eff.type`, because a continuation returning `undefined` otherwise threw a bare TypeError from the condition itself, outside any handler. `chain` has the same guard ahead of its `switch`, for the same reason: once `effectPipe`'s identity pass routed the last step's continuation through `chain`, a missing return there read `.type` off `undefined`. While a Command's `next` ran inside the interpreter's try block, that became a domain `Failure` carrying a TypeError, which is the exact disguise this guard exists to prevent; now that `next` runs outside it, the guard is what turns a bare TypeError into an `EffectTypeError` naming the step. The `Malformed flows` suite pins a missing return at the end and in the middle of a pipeline.

Before this, every one of those mistakes was silent or cryptic: forgetting `Success()` gave `Cannot read properties of undefined (reading 'type')` with no step named, a continuation returning a plain value made `runEffect` resolve to that value so `result.type === 'Success'` quietly took the else branch, and `runEffect(flow)` without an input resolved to the function itself. An `async` step or `next`, the most natural mistake in an async codebase, was reported as "a plain object" with the advice to wrap it in `Success`, which the developer had already done; it is now named as a Promise and pointed at a Command. `effectTypeError` also attaches a handler to that Promise, because a throwing async step rejected it with nothing attached and crashed the process after the caller had already caught the `EffectTypeError`. The handler goes on a native `Promise` only, which is what an async function returns: a Knex or Mongoose query builder also has a `then`, and calling it runs the query.

### Recording and replay (all in `index.js`)

| Export | Purpose |
| --- | --- |
| `recorder(options?)` | Returns `{ onStep, entries, toTrace }`; the `onStep` hook records every Command's result or error, and each `Parallel`'s decision. Options: `redact`, `maxEntries`, `stack` |
| `recordEffect(flowFn, initialInput, opts?)` | Runs a flow for real while recording; returns `{ result, trace }`. Convenience for tests and scripts |
| `replayEffect(effect, traceOrResolver, opts?)` | Replays a tree, feeding recorded outcomes to Commands instead of executing them. Takes a trace or a `Resolver`; returns `{ result, unreached }` for a trace and `{ result }` for a `Resolver`. Options: `context`, `fastRetry`, `hooks`, `onMissing`, `onResolved` |
| `timeTravel(flowFn, traceLog, options?)` | Narrated replay: rebuilds the flow from the recorded input, logs each step, warns on version mismatch and names any unreached steps; returns the bare outcome, since narration is its job |

`fromTrace(traceLog, { onEntry })`, which builds a `Resolver` over the reference trace format and returns it as `{ resolve, missing }`, is **internal**, and `replayEffect` is its only caller. Deliberately not exported: a caller whose traces live in another shape writes a `Resolver` instead, and a caller who only wants to watch a replay uses `onResolved`. The `onEntry` observer is how `replayEffect` learns which entries were handed out; it subtracts those from the trace after the run to produce `unreached`, which is why that field exists for a trace and is absent for a `Resolver`. A step the trace does not hold resolves to `undefined`, as it would from a `Resolver`, so `replayEffect` applies `onMissing` to both, and `missing` describes the step so the refusal still names the path, or the entry number for a trace without paths. It used to throw its own `ReplayError` for a missing step, which `onMissing` never saw, so `'execute'` did nothing for a trace and worked only with a `Resolver`, the one case the tests covered. Two things still win over `'execute'`: a step recorded under another name is a `TimeParadox`, and a missing step that a recorded `Parallel` decision explains is stopped, since production never ran it. Between them those cover every known need, so exporting it would only widen the public surface. The one thing neither covers is _rewriting_ outcomes from a reference-format trace (substituting one step's result, or chaining a fallback), since `onResolved` is an observer whose return value is ignored. Export it again if that comes up; nothing depends on it staying private.

See **Time-travel debugging** below for the invariants these depend on, and the README for each option in full.

### Data flow

```
effectPipe(f1, f2, f3)(input)
  → returns tree of Success / Failure / Command / Ask / Retry / Parallel values
  → f1 runs eagerly here; initialInput is threaded through chain so every
    node in the tree carries it without post-construction mutation; the
    outermost pipeline's input wins over a sub-pipeline's, and effectPipe
    ends with an identity pass so the last step's continuations get it too;
    Success nodes are never stamped

runEffect(tree, context, callConfig?)
  → per-call callConfig is merged over the global configureEffect wiring via
    chainHooks (global outermost), or over nothing when `inherit: false`, so an
    unset hook falls back to the library default; a non-boolean inherit throws,
    and a leftover `retry` key throws
  → executes Commands async, passes results into next(result), repeats
  → resolves Ask by calling next(context), continues
  → resolves Retry via an inner execute() loop (not recursive runEffect),
    so onRun fires exactly once per runEffect call regardless of attempts;
    on exhaustion returns Failure({ retryExhausted: true, lastError, attempts }),
    unless a per-use onExhausted returns a fallback Effect: it executes under the
    retry's `f` path prefix, its success feeds next, its failure propagates
    unwrapped, and a cancelled Parallel branch skips it
  → resolves Parallel by running all effects with the same context, through
    runBounded: Promise.all without `options.limit`, and a pull-by-index worker
    pool with it, so results and paths follow array order either way; the
    first branch to fail cancels the others and its Failure is returned with
    next skipped (array order breaks a same-tick tie, and a replay uses the
    recorded branch); otherwise next gets the array of success values.
    Under `options.settled` no branch aborts its siblings and next receives the
    branch outcomes themselves, so the Parallel never fails on a branch's
    account; an EffectTypeError still escapes. The branches run inside one
    step runner call of type 'Parallel', whose op returns the decision (which
    branch, if any, cancelled the others), so it is recorded like a result
    and a replay hands it back as op(decision)
  → resolves to final Success or Failure; a Failure is restamped with the
    root's initialInput, since a Parallel branch or Retry fallback returns
    one carrying its own subtree's input, which chain never reaches

replayEffect(tree, traceOrResolver, options?)
  → a trace goes through fromTrace(trace, { onEntry }); a function is used as the
    Resolver as-is (typeof check: an entries array is data, so it takes the
    trace path); a malformed trace rejects with a ReplayError
  → installs an onStep that answers each step from resolve(step) instead of
    calling op(), so eff.cmd is never applied and its I/O never happens
  → { result } → handed to the Command's next(result)
  → { error }  → thrown, so the interpreter produces a Failure
  → undefined  → throws a ReplayError unless onMissing: 'execute'
  → otherwise delegates to runEffect, so Ask / Retry / Parallel behave
    exactly as they do in production
```

The `chain` combinator (internal) drives composition: `Success` passes its value to the next function, `Failure` short-circuits, `Command` defers execution, `Ask` wraps its continuation so the chain propagates through it, `Retry` and `Parallel` wrap their continuations via object spread, so their `effect` and `effects` subtrees are carried over untouched. `chain` accepts an optional `initialInput` parameter; `effectPipe` passes the pipeline's starting value through every `chain` call so that `initialInput` is stamped on all nodes, including mid-pipeline `Failure`s, without mutation. `runEffect` loops through the tree with a `while` loop rather than recursion.

`configureEffect` hooks (each can also be passed per call via `runEffect`'s third argument). Retry options are not among them: they are per-use only, passed to `Retry(effect, options)` and merged over the library defaults (`attempts: 3`, `delay: 100ms`, `backoff: 1` flat).

- `onStep`: fires on every Command execution, wrapping the `cmd` call, and once per `Parallel`, wrapping its branches (use for per-command tracing)
- `onRun`: fires once per `runEffect` call; wraps the whole workflow (use for top-level spans); receives `context.flowName` as the third argument; does **not** fire again for Retry attempts
- `onBeforeCommand`: intercepts each Command before execution; receives the Command and the `context` passed to `runEffect`

`configureEffect` is additive: each call adds a layer, the effective wiring is `chainHooks(...layers)` recomputed by `applyLayers` into a single `globalConfig` object on every add or remove, and the returned function removes that one layer wherever it sits, so A installs, B installs, A removes leaves B in place with no guard needed. Calling it with no arguments at all removes every layer; a call whose arguments are all `undefined` is distinguished by the arguments length and adds nothing, because `configureEffect(flag ? hooks : undefined)` is a conditional install, and under the old one-slot rule it reset everything, which was consistent then and a trap once installs became additive. Several configurations passed to one call are merged into one layer, which is the same as installing them separately, so the merge of a single call and the accumulation across calls are one mechanism. This replaced a one-slot rule under which a later call displaced the earlier wiring, an omitted key reset its slot, and the returned function restored a snapshot; the three rules existed only because a slot could hold one value, and each needed its own paragraph. A per-call `callConfig` is merged over that wiring by the same `chainHooks` merge, so the two paths order and unwind identically; `inherit: false` merges it over nothing instead, so an unset slot falls to the library default. `globalConfig` is the only derived form of the layers, and a slot no layer defines is absent from it rather than held as a default: the library default is chosen where the hook is used, in `runEffect`, which is the one place that reads the wiring. For a while the merged result was copied into four module-level variables, one per hook, that `runEffect` then packed back into an object to merge again; every change to the hook set had to touch the variables, the copy, and the repacking together, and a missed slot fell back to a no-op silently. A call with no configuration of its own uses the installed wiring as it is, without a merge. A non-boolean `inherit` throws a `TypeError` rather than being coerced, since `'false'` quietly inheriting everything is the silent behaviour the option exists to remove. The option exists because per-call config used to displace slot by slot: `recordEffect` inside an instrumented application produced a run with no spans, and `replayEffect` had to install no-op `onRun` and `onBeforeCommand` wrappers to smother the global ones. Now `recordEffect` simply passes its recorder and `replayEffect` passes `inherit: hooks`, so under `hooks: true` the resolver sits innermost and a configured `onStep` observes the replayed steps while the Command still never executes. Slot-by-slot replacement was dropped deliberately when the option went from a three-way string to a boolean: it was the behaviour that caused the recording bug, replacing one slot is only meaningful when you know what the others hold and there is no getter, and the one case that needs it, a per-call decider under a global decider, has no example outside replay, which ignores the wiring anyway. Merging is only trustworthy while every nested hook is a watcher: a global `onStep` that never calls `op` would silently starve an inner per-call hook, which is fine for everything in this repository but is a property of the current hook shapes rather than a guarantee. The name was chosen over `global` (Node's alias for `globalThis`) and `ambient` (a new noun the docs never otherwise use). Recording and tracing installed globally can go into one call or two; the examples' `enableRecording` and `enableTelemetry` install a layer and return its remover. Recording stays a reference file rather than a library export for the reasons given under Observability, not because installing hooks clobbers anything any more.

The raw hooks are powerful: a hook decides whether the Command runs at all, which is how replay suppresses I/O, and what it throws becomes the flow's outcome: a `Failure` if it throws before the Command's function has succeeded, a rejected run if after. That power is wrong for anything that only watches, and it caused two real bugs here: the tracing example serialized its input before calling `pipeline()`, so a cyclic input left flows unexecuted, and `recorder` let a throwing `redact` turn a successful run into a `Failure` carrying the redaction bug while recording an entry that claimed the Command had thrown. The internal `observeSteps(handler)` now holds that contract in one place: `op` always runs, its result is always returned, its error always propagates, and anything the observer throws is dropped. Keep it minimal and unexported. `recorder` is its only caller and needs only `onStep`, so there is no `onRun` branch and no error-reporting channel, and an exported second route to the raw hooks would widen the surface for integrations nobody has written. It briefly was exported, as `observe`, with both branches; that cost 270 bytes gzipped for one internal call site and no consumer, which is the same argument that removed `tap`.

Trace entries carry `durationMs`, rounded to microseconds, because `observeSteps` measures the span around `op` anyway and nothing else recorded timings. `timeTravel` narrates it, looking the entry up by path, or by position for a trace that carries none.

The function `configureEffect` returns removes that call's layer and nothing else; it is idempotent, and it is for code that installs hooks over someone else's wiring; a bare `configureEffect()` is the clean-slate reset the suites use, described below. Under the one-slot rule the returned function restored a snapshot instead, first unconditionally, which let two callers releasing in interleaved order discard each other's hooks, and then only while that snapshot was still current, which meant a late restore silently did nothing; a layer can be removed from the middle of the list without either problem.

Retry options are not part of that wiring and never were a good fit for it. `attempts`, `delay` and `backoff` describe how one dependency misbehaves, which is a property of that dependency rather than of the process, and a shared `const flakyNetwork = { attempts: 3, backoff: 2 }` passed to each `Retry` covers the repeated case in ordinary JavaScript, explicitly and greppably, without a global anyone reading the flow cannot see. Removing the slot deleted two justifications with it: `replayEffect` no longer has to carry `retry` across the `inherit: false` boundary by hand, which it had to because `inherit: false` dropped it along with the hooks and a `Retry` that production ran under a configured `attempts` then exhausted early on replay; and the Limitations entry about a `callConfig` delay always losing to a per-use one is gone rather than fixed, since there is no longer a second place for a delay to come from. A leftover `retry` key throws a `TypeError` from `configureEffect` and from `runEffect`'s `callConfig`, checked before any layer is installed so a refused call leaves the wiring untouched; silently ignoring it would turn a configured `attempts: 5` back into 3 without a word, which is the same silent degradation that makes a non-boolean `inherit` throw. The guard is migration scaffolding and comes out at 1.0.

`Retry`'s `attempts` must be a positive integer, and `0` throws rather than meaning run once. Two reasons, and the coherence one is the load-bearing half: a `Retry` that does not retry is not a `Retry`, and reading one at a call site should not require checking whether an option has quietly turned the node into something else. The second is narrower. `attempts: 0` was the one spelling that made `onExhausted` a catch at no cost: it takes control after an I/O fault anywhere in an arbitrary tree and returns an arbitrary Effect. Since aborts and I/O faults were told apart it can no longer answer an abort, which is the property worth protecting, but it still answers any I/O fault, and `attempts: 1` does that just as well while running the tree twice. So rejecting `0` removes the free spelling rather than the loophole: recovering that way always costs a visible re-execution, and the error message points at the two things that actually solve the motivating cases, branching on the outcome as data and `Parallel`'s `settled` for isolating a branch. A companion option was designed and dropped for the same reason: `settled` had already closed the batch-isolation hole that was the only case with no other expression.

That global state is also why the test suite needs care. Hooks outlive a suite, so every `describe` that could inherit another's wiring guards with `beforeEach(() => configureEffect())`, a bare call. It has to be bare: `configureEffect({})` adds an empty layer and removes nothing, and eight suites guarded that way for a while after installs became additive, so they ran under whatever the previous suite had left installed. The gate stayed green only because the leaked hooks wrote to arrays nobody read later. The `Core` suite went unguarded for a while and was safe only because it is declared first, which is positional luck rather than isolation: a suite added above it, or a future split into several files, would silently change what it runs with.

The internal `chainHooks` does that merging, and it relies on `onStep` and `onRun` being wrappers around an `op`: nesting them composes, with the first configuration outermost, so a thrown Command unwinds from the last back to the first. The installed layers come before a per-call configuration, which is what puts global wiring outermost. `onBeforeCommand` is an observer, so interceptors run in sequence instead. Keep those semantics if the hook shapes ever change. It was briefly exported; folding it into `configureEffect` removed an export and reads better at the call site, since a merge is only ever useful on the way into a configuration.

### Sharp edges pinned by tests

Several semantics are surprising enough that the `Documented sharp edges` suite exists to keep them from changing silently, and each has a Limitations entry.

The interpreter distinguishes three kinds of failure, and that distinction is the answer to a family of bugs rather than one. A `Failure` a step returned is an **abort**: the flow has decided, and the shell is what acts on it. A `Failure` the interpreter built because a Command's function threw is an **I/O fault**: that is what `Retry` exists for. An `EffectTypeError`, a replay fault, or anything thrown by a continuation or a pure step is a **harness error** and not an outcome at all: `runEffect` rejects with it. A harness error is thrown, and the error factories mark it with the `harnessError` symbol so the Command catch rethrows it; that mark sits on an `Error` the library created, never on flow data. An I/O fault is an internal state, `{ type: 'IoFault', error, initialInput }`, that only `execute` returns: the Command catch and a `Retry` exhaustion produce it, `Retry` and `Parallel` read it, and it becomes a plain `Failure` wherever it would reach user code, at the `runEffect` boundary and in the outcomes a settled `Parallel` hands `next`. So every `Failure` a caller or a step ever holds is plain data, and whatever a step returns is an abort. A continuation cannot forge the state, since the loop accepts only the six public types. Provenance used to be a hidden symbol on the `Failure`, and it leaked: a settled `Parallel` handed marked outcomes to `next`, `chain`'s spread dropped the mark only when the pipeline had an input, and two deep-equal `Failure`s meant different things to `Retry`. Keep provenance out of anything user code can hold.

Without that distinction `Retry` could not tell "the socket died, try again" from "this email is already taken", and three bugs followed from the one gap. It re-ran a database lookup four times for an answer that could not change. It buried the domain error under `{ retryExhausted, lastError, attempts }`, so the shell had to unwrap a claim about retrying that had nothing to do with the outcome. And `onExhausted` answered a deliberate abort and reported `Success`, which is the loophole that made the no-catch ceiling untrue. `Retry` now returns an abort immediately, unretried and unwrapped, and `onExhausted` never sees one, so the ceiling is finally a sentence that holds: you can recover from an error your I/O produced, and you cannot catch an abort. It is not a complete closure of catch, since `onExhausted` still answers an I/O fault raised anywhere inside an arbitrary tree, and that is deliberate: recovering from I/O is what the option is for, and the property worth protecting was that an abort reaches the shell.

Two pieces of guidance stopped composing when provenance landed, and both are documented now rather than fixed, because each is the correct behaviour meeting advice written before it. The README tells a reader to catch inside the `cmd` function when the I/O can reject and return the miss as a value; doing that makes the failure an abort, so a `Retry` around that step makes one call and never tries again, silently. The rule the README now states is that catching and retrying are alternatives: catch it in the function when the flow should handle it as data, let it throw when `Retry` should act on it. And the PII guidance, log `result.error` rather than the whole `Failure`, was written for the top-level result, which a settled `Parallel` never produces because it never fails; what `settled` hands `next` is an array of `Failure` nodes carrying the same `initialInput`, and reporting them is the entire point of the mode, so the guidance now covers that shape too. Both were found by an audit that writes the flow a careful reader would write after reading each documented sharp edge, which is worth repeating whenever behaviour changes, since here the code moved and the guidance did not move with it.

Two details in that machinery are load-bearing. A retry exhaustion is itself an I/O fault, because it came from I/O, which is what keeps a nested `Retry` retrying an inner one rather than treating its exhaustion as an abort. And the doctrine the whole thing rests on is the one the README already stated: a domain outcome is returned, never thrown. A value thrown by a `cmd` function is an I/O fault by definition here, so a `cmd` function that throws a business error has told the interpreter something it did not mean, and the interpreter will act on it. That was documented guidance before and is enforced behaviour now.

The definition is narrow on purpose, and for a while it was not. The Command branch of `execute` had one try block around three things, the `onBeforeCommand` interceptor, the step runner that calls `cmd`, and `eff.next(result)`, and stamped whatever it caught as an I/O fault. `next` runs every pure step up to the next Command, so a TypeError in pure code after a retried Command re-ran the Command, which had succeeded, and a guardrail that threw to veto a Command, which the README documents as "throw to abort", was retried and could be answered by `onExhausted`. The block is now three regions. An interceptor's throw is an abort, since a veto is the flow being stopped rather than the I/O failing. The step runner's throw is an I/O fault unless the Command's function succeeded. The step runner includes every `onStep` hook, so a telemetry hook whose exporter failed after the function returned was retried, and charged the card once per attempt. `op` is therefore wrapped to record whether the function succeeded, and when it did, a throw from the runner is a bug in a hook and rejects the run. A hook that throws without calling `op` stays a fault, because that is how replay reports a recorded error and how a circuit breaker written as a hook refuses a call. The one gap is a `hooks: true` replay whose hook throws after a replayed step: replay supplies the result without calling `op`, so the throw counts as a fault there, and since nothing executes during a replay, nothing is repeated. The wrapper returns a synchronous function's value as it is, so a hook calling `op()` without `await` sees what it always saw. `next` runs outside both, so a throw there rejects the run, which is what a throw from `Ask`'s `next`, `Parallel`'s `next`, `Retry`'s continuation, and `onExhausted` already did: they were never inside a try, and the Command's `next` was the one continuation whose throw became an outcome. Such an error is not marked with `harnessError`; the mark exists so a catch knows to rethrow, and no catch surrounds a continuation any more. `Parallel` holds a branch's thrown error rather than letting `runBounded` reject with it: it aborts the scope, lets every branch settle, and throws the first by array index. Rejecting `Promise.all` at once left siblings running unobserved and stopped a `limit` worker, which was true for an `EffectTypeError` before and would have been common once every bug in a branch's code threw. The `Where a throw comes from` suite pins each region, the branch cancellation under the default, `settled`, and `limit`, a replay rejecting rather than returning a `Failure`, a hook throwing after a successful Command rejecting with the Command run once, the two hook throws that stay faults (without calling `op`, and rethrowing the function's error as another), and a synchronous function's value reaching a hook without a promise.

`Retry` repeats the entire wrapped tree on every attempt, including Commands that already succeeded, because the retry loop calls `execute(eff.effect)` again rather than resuming. That is true of an I/O fault; an abort is not retried at all, so the sharp edge is narrower than it was but has not moved. The form that catches people is subtler than the pipeline the guidance warns about: a Command's `next` is part of the tree, so `Retry(Command(cmd, next))` where `next` continues the flow wraps everything downstream, however far that reaches, while looking like it obeys the advice to wrap one Command rather than a pipeline. Found by building a booking saga with two nested retries written that way: an exception in the last step charged the card nine times, because each enclosing `Retry` saw the propagating I/O fault and re-ran its whole remainder. The rule that actually holds is that a retried Command keeps its default pass-through `next` and the branching happens in a later pipeline step, which is what the README and the second `Documented sharp edges` test now say. The semantics are unchanged: this is guidance and a pinning test rather than a guard, because the hazard is not visible in the data and a shape check would ban legitimate trees. `Retry(effectPipe(charge, receipt))` charges three times when the receipt step fails twice, and the run still reports `Success`. The semantics are defensible, since retry means run this tree again, but the README's "wraps any Effect tree" invites exactly the dangerous construction, so both the JSDoc and the Retry section now say to wrap the failing Command instead. If this is ever changed to resume rather than repeat, the pinning test is the one to read first.

`Parallel` takes `options` as `{ limit, settled }`, and the second argument is sniffed: a function is `next`, anything else is the options, so `Parallel(effects, { limit: 5 })` needs no placeholder and every existing call is untouched. The sniff has precedent in `replayEffect`, which tells a `Resolver` from a trace by `typeof`. Both options exist because a batch was the one shape the primitive could not express. `Parallel`'s first-failure rule is right for a fan-out whose branches are parts of one answer, and wrong for a fan-out whose branches are independent records: there, one unmodelled exception became the whole run's `Failure`, cancelled its siblings mid-flow, and left work half done, which in a billing job meant a charge with no invoice and a rerun that charged again. Nothing in the library could isolate a branch, since `Failure` propagates and there is no catch; the nearest expression was the `onExhausted` spelling described under `Retry`'s `attempts` above, which runs the tree again and would charge the card twice. `settled` is the honest version of that workaround.

A settled `Parallel` hands `next` the branch outcome nodes, `Success` and `Failure`, rather than a `{ status, value }` shape borrowed from `Promise.allSettled`: the library already has a vocabulary for succeeded-or-failed, and a second one meaning the same thing would be a new thing to learn for nothing. `EffectTypeError`, a replay fault, and a throw from a continuation or pure step all still escape a settled `Parallel`, which is the one line that keeps the mode honest: it catches outcomes that were always possible, not mistakes, and a flow bug going quiet inside a batch is exactly the failure the interpreter's rethrow exists to prevent. `limit` is deliberately per-use with no `configureEffect` default, since it describes the resource being protected rather than the process. A limit never reaches a trace: paths come from array index, so a flow recorded with one replays identically without one, and replay ignores limiting entirely because nothing is executing.

`Parallel` cancellation is cooperative. The first branch to fail aborts an `AbortController` scoped to that `Parallel`, linked to the enclosing one so cancellation nests. Two levels of effect follow. A cancelled branch starts no further Commands, checked at the top of `execute`'s loop, which needs nothing from user code and is where most of the benefit is. Stopping the Command already in flight needs its thunk to accept the `AbortSignal` it is handed, which is why `cmd` is now called as `cmd(signal)` inside a `Parallel` and with no argument anywhere else: passing an argument only where it means something keeps a thunk written as `(x) => ...` from silently receiving one. A thunk that ignores the signal runs to completion, so a branch whose first Command is a write can still write after a sibling has failed, which is what the pinning test covers. `Parallel` still awaits every branch before returning, deliberately: returning early would leave cancelled work running unobserved after the Failure, with its rejections unhandled. The triggering branch is tracked separately from branches that failed because they were cancelled, so a cancellation never displaces the real error; when several branches fail in the same tick the first by array order wins, which is the older documented behaviour and is pinned.

Every `Failure` carries `initialInput`, stamped by `chain`, alongside the full error. Neither is trimmed and neither should be: a test asserting on a Failure and a developer reading one both need the whole thing. The value is the input of the flow that was called, at any depth. `chain` used to stamp only nodes that had none, and a step returning a sub-pipeline stamps that sub-pipeline's own start first, so whether the flow's input ever reached the root depended on the head node's type: a Command was rebuilt through its constructor and lost the inner stamp, while `Retry` and `Parallel` were rebuilt by spread and kept it, and a `Failure` passed through untouched. A hook-based recorder reads the root's stamp as the trace's input, so a flow whose first step returned a `Retry`- or `Parallel`-headed sub-pipeline recorded the sub-pipeline's input, and `timeTravel` rebuilt the flow from that wrong value and reported `Success`, since replay feeds recorded results and never runs anything. `chain` now overwrites, and `effectPipe` ends with an identity pass, `chain(tree, Success, start)`, because `chain` re-stamps a sub-pipeline's nodes only through the continuations it wraps and the last step has no later step to wrap them. That still leaves the subtrees a `Retry` holds in `effect` and a `Parallel` holds in `effects`, which the interpreter executes directly rather than reaching through a continuation, so a `Failure` escaping a branch or a fallback arrived carrying the subtree's own input or none; `runEffect` therefore reads the root's stamp once and restamps the final `Failure` with it, which is the single point every outcome leaves through. The two mechanisms cover different things and both are needed: the interpreter's restamp is what makes the guarantee hold at any depth for a run, and `chain`'s stamping is what makes it hold for a `Failure` produced by walking a tree by hand in a test, which never passes through `runEffect`. `Success` nodes are never stamped: nothing reads the input off a terminal value, and the previous behaviour stamped them or not depending on whether the last step returned a `Success` directly or through a Command's `next`, which is why `assert.deepEqual(result, Success(v))` used to hold for some flows and not others. The `initialInput stamping` suite pins the three head shapes, a `Failure` from a sub-pipeline, two levels of nesting, and a bare sub-pipeline keeping its own input when nothing encloses it. `recordEffect` was never affected, since it takes the input as an argument; the hook path has no such argument, which is the deeper reason the tree carries the value at all. PII control is split deliberately. `redact` is the single mechanism for a trace, and the shell owns what reaches logs, so the guidance is to log `result.error` rather than serialize a whole Failure.

`redact` therefore has to see everything a trace holds, and for a while it did not. It covered Command results only, so a caller who installed a correct redact still shipped `initialInput` verbatim, the `context` verbatim, and any custom property on a thrown error: in the registration flow that is the plaintext password in two places and the auth token in a third. It now receives results, serialized errors, and the trace's own `initialInput` and `context`, with a `kind` argument of `'result'`, `'error'`, `'initialInput'`, or `'context'` to tell them apart. Keep that coverage complete if the trace format grows another field, since a field redact cannot see is a field that leaks. An absent `initialInput` or `context` is left `undefined` rather than passed through, so a redact that spreads its argument cannot turn nothing into an empty object.

### Time-travel debugging

Because a flow is data, a production run can be recorded and replayed later. Recording is just an `onStep` hook, so it needs no change at call sites: install `recorder().onStep` via `configureEffect`, or pass it as per-call config. It merges with tracing whether the two are installed in one call or two. `recordEffect` is the convenience wrapper for tests and scripts.

Seven invariants hold the design together; breaking any of them breaks replay in a way tests may not catch:

- **Replay drives the real interpreter.** `replayEffect` calls `runEffect` rather than walking the tree itself, which is why `Ask`, `Retry`, and `Parallel` replay correctly and why replay semantics cannot drift from execution semantics. The interpreter's only execution point is `await localStepRunner(cmdName, 'Command', op, cmdPath)`, which hands `onStep` a wrapper around the Command's function as `op` instead of calling the function; the wrapper only records whether the function succeeded. Replay's `onStep` never invokes `op` unless `onMissing: 'execute'`, so **no side effect can occur by default**. Preserve that single-execution-point property: a Command executed anywhere else in the interpreter would be invisible to both recording and replay. A `Parallel` also goes through the step runner, but its `op` performs no I/O of its own; it runs the branches, whose Commands each reach the execution point as usual.
- **Path matching, with positional matching for traces that carry no paths.** Every step carries a `path`: its position in the Effect tree, numbered sequentially within a subtree, with each `Parallel` branch and each `Retry` attempt opening its own prefix (`0p1/0r2/0` is branch 1, retry attempt 2, first Command; a retry's `onExhausted` fallback opens `0rf/`). A path depends only on the shape of the tree, never on the order branches finish in, so it is order-independent **and** paradox-detecting at the same time. `fromTrace` matches by path whenever every entry has one. Duplicate paths throw, since a collision would reintroduce the failure paths exist to prevent. A trace whose entries carry no path (recorded before paths existed, or written by hand) is consumed positionally, each entry checked against the Command the flow asks for; exact for sequential flows, and unable to tell `Parallel` branches apart. There is no matching option any more. `strict` used to choose between that positional mode and a per-Command name-queue mode, which was the only way to replay `Parallel` before paths, and **the name-queue mode was the bug paths fixed**: it paired a step with the next recorded entry of the same name, which is completion order, so two `Parallel` branches calling the same Command swapped results whenever replay timing differed from production, and the replay still reported `Success`. Once paths made it unnecessary the option was removed rather than left as a footgun; a `Resolver` remains the way to match by any other rule. The positional resolver refuses a step whose path shows it is inside a `Parallel` (a `p` segment), with a `ReplayError` that says to add paths, because a positional answer there would be right only when the replay happened to finish in production's order, and silently wrong otherwise.

- **The hook contract carries the path as a fourth parameter.** `onStep(name, type, op, path)`. Three-parameter hooks keep working, and `chainHooks` forwards the path through nested wrappers. A hand-rolled wrapper that calls `inner(name, type, op)` without forwarding `path` silently produces a trace with no paths, which then falls back to legacy positional matching: correct for sequential flows, and the old swapping bug for `Parallel`. Forward the fourth argument in anything that wraps `onStep`. `onStep` also wraps each `Parallel`, with `name` and `type` both `'Parallel'`; its `op` runs the branches, so a hook has to call it, and the interpreter rejects with a `TypeError` when the runner returns without `op` having run rather than continue with no branch results. Only a replay passes `op` an argument, the recorded decision, and only the innermost hook can pass one, since `chainHooks` hands outer hooks a closure that takes none. The replay's hook is per-call and therefore innermost, which is what makes that work.
- **A cancelled `Parallel` replays its recorded decision.** Which branch cancels a `Parallel` is decided by timing, which is exactly the kind of value the README tells users to put inside a Command, and for a while the library broke that rule itself: the decision was never recorded, a replay reached its own decision at replay speed, and a checkout whose charge was declined replayed as the `AbortError` of the stock reservation it had cancelled, because the reservation's single step resolved before the charge branch reached its second. A branch production stopped between steps could also run on in a replay and ask for a step that was never recorded. The decision is now recorded as the `Parallel`'s own entry at its path (`0p`): `{ cancelled: false }`, `{ cancelled: true, branch: i }`, or `branch: null` for a `Parallel` an enclosing one cancelled. A replay of a cancelled `Parallel` reproduces it rather than recomputing it: nothing aborts the scope, each branch runs its recorded steps, a missing step in a branch the decision cancelled is where production stopped it (`fromTrace` throws a `replayCut` marker and the interpreter returns that branch as cancelled), and the result is the recorded branch's failure. If that branch no longer fails, the `Parallel` raises a `TimeParadox`, and so it does when the decision names a branch past the end, which means the shape changed since the recording; falling back to timing there let the first remaining branch the replay reached decide, which is the bug this fixed. A negative branch is never recorded, so it is not a decision and replays by timing like anything else that is not one. Nothing in a replay waits for a cancellation, so a diverged flow cannot hang. A missing step anywhere else is still a `ReplayError`. A trace without decisions, and a Resolver that answers a `'Parallel'` step with anything but a decision, replay by timing as before, and a `'Parallel'` step neither advances `index` nor reaches `onResolved`. Marking each step that finished after its branch was cancelled was considered and rejected: it fixes the declined checkout but not a branch stopped between steps, which leaves no step to mark, nor two branches failing at almost the same moment. The recorder does not `redact` a decision, since it holds no user data and a `redact` that rewrites every result would otherwise destroy it.
- **`fastRetry` exists because retry options are per-use.** A delay is written at the call site and nothing outside the node can override it, since there is no configured retry to override it with. `zeroRetryDelays` therefore rewrites `Retry` nodes to `delay: 0, backoff: 1` lazily, through their `next` continuations; without it, replaying a flow that retried in production waits out the production backoff.
- **A replay fault is a harness error, not an outcome.** `effectTypeError` and `replayError` both mark their errors with the `harnessError` symbol, and the interpreter's Command catch rethrows anything carrying it rather than folding it into a `Failure`. That is what keeps a replay fault out of reach of everything that legitimately handles a domain failure: a Command's `next`, `Retry`'s `onExhausted`, and the outcomes a settled `Parallel` collects. Without it the `onMissing` guard was defeated by both of the latter, and a truncated trace replayed as a `Success` whose branches each carried the `ReplayError` as though production had returned it, which is the worst possible answer from a debugging tool. `replayEffect` catches the fault at its own boundary, where nothing downstream can absorb it, and returns the `Failure` this function has always returned, so the public contract is unchanged. A replay fault carries a second mark, `replayFault`, which is how that boundary tells one from an `EffectTypeError`: a malformed flow is a bug in the flow rather than a problem with the trace, so it keeps propagating. A new harness error gets the mark rather than a new name for the interpreter to know about; matching on `name` would have missed `TimeParadox`, which overrides the name `replayError` sets.
- **The outcome wrapper is load-bearing.** A `Resolver` returns `{ result }`, `{ error }`, or `undefined` for "not recorded". The wrapper keeps a Command that legitimately returned `undefined` (`{ result: undefined }`) distinct from having no recording, which is what makes the `onMissing` guard trustworthy.

Two further details: `hooks` defaults to `false`, so a replay cannot reach a telemetry backend or a guardrail that performs I/O; and errors cross the trace via `serializeError` / `reviveError` because `message`, `stack`, and `cause` are non-enumerable on `Error` and a plain `JSON.stringify` would silently drop them; `cause` is carried recursively since it is often an `Error` itself. An `AggregateError`'s `errors` is non-enumerable for the same reason and carried the same way, one serialized entry each, because that is where its detail lives: Node's refused connection to `localhost` has an empty message and one entry per address it tried. It travels under its own key, `__errors`, beside the `__error` marker, because a validation error carries an enumerable `errors` as data and revival has to restore each with the enumerability it had; only a non-enumerable array takes that path. Non-`Error` values pass through unchanged, so a Command that rejected with a string still replays as a string. `reviveError` defines `name` and `cause` as non-enumerable own properties, matching where a native Error keeps them, because the README's determinism check is `assert.deepEqual(replayed, result)` and Node compares own enumerable keys: assigning `e.name = ...` made every revived error carry an extra key and the check failed for every `Failure` while passing for every `Success`, which is exactly the half of the check that matters. A subclass instance still revives as a plain `Error` (the trace carries a name, not a prototype), so the check is documented as holding for plain errors.

What replay proves has a boundary worth stating, because the README used to demonstrate only the side of it that works. A replay checks that the flow still asks for the same Commands in the same order and still handles the same answers. It cannot check what the flow computes, since every Command's result comes from the recording rather than from the code under test: change the arithmetic in a pure step, replay the recording of the run that got it wrong, and the next Command is handed the old value straight back, so the replay reports `Success`, returns the pre-fix outcome, and has nothing to flag. Found by recording a refund flow that refunded shipped items, fixing it, and watching the replay report the buggy amount as the fixed flow's answer. Nothing in the library can detect this, and recording arguments would not help either, since the recorded arguments would be the old ones too; the fix is to test a value change against the pure step that computes it and keep replay for the question it answers. The same experiment showed that `unreached` is a proof only when the step that goes away was the last the flow reached: removed from the middle it shifts every later path by one, the replay stops at a `TimeParadox`, and `unreached` then lists what the replay never got to rather than what the fix made unnecessary. `timeTravel` already suppresses its unreached warning after a paradox for that reason; `replayEffect` still returns the list, so the README now says what it means in that case.

A trace records results and never Command arguments, and that is settled rather than pending. Arguments live in the Command's closure, and recording them was considered as a gap for guardrails, caching, and reading a trace by eye; it is not one. The replay premise makes arguments reconstructible: given `initialInput` and the recorded results the flow is deterministic, so replaying to a step rebuilds the exact closure, which covers debugging. A guardrail vetoes on the context, which carries tenant and request identity by design, and anything a Command wants a hook to see goes in `meta`, which `onBeforeCommand` already receives, so a cache key has a home too. Recording arguments would double the PII surface of a trace for no replay benefit, since arguments are usually the sensitive half of a call, and every recorded field is another one `redact` must cover. The one thing that would undermine the argument is a Command whose arguments depend on something nondeterministic computed outside a Command, and the README already classes that as a bug to fix by wrapping the nondeterminism in a Command.

Recorded results are snapshotted by the internal `snapshot`, not stored by reference. Without it a later step that mutates a returned object rewrote what the trace said an earlier step returned, and because `toTrace` runs after the flow finishes, the mutation was already baked in by the time a sink serialized it: the trace recorded a value production never saw, and a replay fed that value back. It uses `structuredClone` where available, falls back to a JSON round trip, and falls back again to the reference for values that can be neither, since dropping the entry would be worse. Redaction runs first, so nothing sensitive is cloned before being stripped. Replay snapshots again on the way out, in `entryToOutcome`, for the same reason in the other direction: handing the flow the entry's own object let a replayed step that mutates its result rewrite the trace, so replaying one trace twice gave two answers, and a caller mutating a replayed `Failure`'s error did the same.

A trace therefore keeps data, not objects, and that is settled. `structuredClone` drops classes (a money object or an ORM entity comes back plain, a `Buffer` as a `Uint8Array`, an error inside a result without its custom properties), and a JSON sink loses more (`Date` to string, `Map` to `{}`). Two fixes were considered and rejected. Keeping the reference for class instances brings back the mutation bug for exactly the values most often mutated, ORM entities, and cannot survive JSON anyway, so it would fix in-process replay and leave the production path as it was. A value encoding, tagged forms for `Date`, `Buffer`, `Map` and the rest plus per-class codecs, was declined as more machinery than the problem warrants. The answer is how Commands are written: return plain data, converting with a small named function inside the Command's function, and copy the fields `next` branches on out of a caught error. The README states this in Recording in Production and in Limitations.

`TraceLog` is the reference trace format, not a contract: `replayEffect` also takes a `Resolver`, so any storage shape works by writing one.

`timeTravel` narrates through `replayEffect`'s `onResolved` hook rather than by wrapping a `Resolver`, which is why it can pass the trace straight through and why `fromTrace` needs no public export. Keep that split: `onResolved` is the seam for _observing_ a replay (logging, counting, step assertions), and a `Resolver` is the seam for _supplying_ outcomes. `replayEffect` returns `{ result, unreached }` rather than the bare state, mirroring `recordEffect`'s `{ result, trace }`; `timeTravel` narrates the same list and returns the bare outcome, because narration is its whole job and a caller who wants the entries as data has `replayEffect`. `unreached` exists because a flow that stops issuing Commands early mismatches nothing: no `TimeParadox` fires, the replay ends in `Success`, and the recorded steps it never asked for are the only evidence of the divergence. A regression test for a fix that deliberately skips a step asserts which step; every other recording asserts the list is empty. It rides beside the result rather than on it so the flow's outcome stays exactly what production would have returned, and rather than behind an observer option (which it briefly was) because a value handed to a callback exactly once after completion is a return value in disguise, and the `let unreached` it forced into every test was the tell. It is absent, not empty, for a `Resolver`: an empty list would claim knowledge the replay does not have. `timeTravel` still narrates the list, but not after a `TimeParadox` or `ReplayError`, since the flow never got past the divergence and the error already names it. Narration that reaches for a `Resolver` is a sign the wrong seam is being used.

### TypeScript

Full generic type declarations are in `index.d.ts` and referenced via the `types` field in `package.json`. Type-level tests live in `test/types.test-d.ts` and run via `tsd` as part of `npm test`.

`index.d.ts` is hand-maintained beside `index.js`, so the two can drift. Three mechanisms guard the drift: the `Declaration parity` test pins the export lists to each other in both directions; `tsd` checks the declarations against `test/types.test-d.ts`; and `npm test` runs `tsc -p jsconfig.json`, strict `checkJs` over `index.js`, `test/all.js`, and `examples/*.js`. That last leg reads the declarations too, not only the JSDoc: `test/all.js` imports `../index.js`, and TypeScript resolves that to the sibling `index.d.ts` before it considers the JavaScript, so the test suite is checked as a strict consumer of the public types. The leg was added after a narrowing error in the interpreter shipped through a green gate and was found in an editor, the second time a lens existed but was not in the gate. It then had to be widened twice for the same reason. The config listed `index.js` alone while `test/all.js` opened with `// @ts-check` and was annotated to typecheck, so an editor showed errors there that the gate never saw. And it ran without `strict`, while VS Code checks JavaScript with `strictNullChecks` and `strictFunctionTypes` by default and consults only `tsconfig.json` or `jsconfig.json`, so it ignored the old `tsconfig.check.json` and reported errors against a green gate. The file is named `jsconfig.json` and is strict precisely so that the editor and the gate read one configuration; keep both properties, and add any checked JavaScript that lives in this repo to its `include` list. `test/types.test-d.ts` is in the list too, which is possible only because its deliberate errors are `@ts-expect-error` directives rather than `expectError` calls (see below). **Check `npm test` by exit code.** `tsd` failures print neither "passing" nor "failing", so piping the output through `grep -E "passing|failing"` hides them entirely, which is how `runEffect`'s declaration stayed deleted through several edits here while every other check reported green. It was removed as collateral by a slice that targeted an adjacent block, so after any structural edit to `index.d.ts`, compare the runtime exports against the declared ones rather than trusting the diff.

Deliberate type errors in `test/types.test-d.ts` are written as `// @ts-expect-error` directives, never as `tsd`'s `expectError(...)`. Both assert that the next expression fails to typecheck, but only the directive is understood by the compiler itself: `expectError` leaves a real diagnostic in the file that `tsd` swallows and every other tool reports, so with it the file showed ten red lines in VS Code and could not be part of the `tsc` gate, which is how a green `tsd` and a red editor coexisted for a while. With the directive, TypeScript suppresses the error and reports `Unused '@ts-expect-error' directive` if it ever stops occurring, and `tsd` fails on that diagnostic, so the assertion is as strong as before (verified by making a suppressed line valid and watching `tsd` fail). What is given up is `expectError`'s check that the error is one of a few specific codes: a directive is satisfied by any error on the line, so keep each suppressed expression small enough that only the intended mistake can fail it, and give every directive a reason. The directive covers exactly one line, so a suppressed expression stays on one line.

`Effect<T, E, Ctx>` carries three type parameters: value type, error union, and context type. `Ctx` flows through `AskState`, `CommandState`, `RetryState`, `ParallelState`, and all `effectPipe` overloads. `Ask<T, E, Ctx>` types the context callback parameter, and `runEffect<T, E, Ctx>` enforces that the supplied context matches. `Ctx` defaults to `unknown` so existing code without context typing is unaffected.

Error unions need explicit return annotations. A step written as `(i: User): Effect<User, 'taken'> => ...` contributes `'taken'` to the pipeline's union, but the same step left to inference from a bare `Success(x) | Failure(y)` return type yields `E = unknown`, and one `unknown` absorbs every other member of the union, so `result.error` degrades to `unknown` for the whole pipeline. Annotate `Effect<T, E>` on any step whose error type is meant to survive, and write type-level examples that way.

`effectPipe` is declared as 20 overloads, one per pipeline length, the same ceiling as Effect-TS's `pipe`; it was 8 until a nine-step pipeline, written to test the limit, failed to compile with `Expected 1-8 arguments`. Nothing in this repository comes close: the longest pipeline in the README, the tests, and the examples has four steps. The overloads are generated in one shape, numbered values `T0` to `Tn`, then errors `E1` to `En`, then `Ctx`, so extending the ceiling means regenerating the block in that shape rather than editing one overload by hand; no caller passes these type parameters explicitly, which is what made renaming them from letters free. Two alternatives were rejected. A single variadic signature built from recursive types removes the ceiling, but an inline step with no annotation loses the parameter type it is inferred from the previous step, and its errors are far harder to read. A catch-all overload past the ceiling that accepts any length untyped is worse, because a long pipeline would silently stop being checked while looking typed; a compile error at 21, with nesting as the workaround, is the honest failure. The tsd file pins 9 and 20 steps, including an unannotated inline last step, the full error union, and the context, plus 21 rejected and the nested form accepted.

`Retry`'s declared error is `E | RetryExhaustedError<E>`, and both halves are deliberate. An abort the wrapped tree returns leaves unretried and unwrapped, so its `E` escapes as it is; an I/O fault the loop cannot get past becomes `{ retryExhausted, lastError, attempts }`, where the inner `E` survives only as `lastError`. `RetryState`'s `effect` field is typed `Effect<T, any, Ctx>` because the node's error is declared on the node itself rather than read off the wrapped tree. The declaration once claimed `E` alone, which made `result.error` lie for every exhausted `Retry`, and then `RetryExhaustedError<E>` alone, which stopped being true when aborts stopped being retried; the tsd assertions in the Retry section pin the current shape. With a per-use `onExhausted` the declared error is `E | E2`, the abort's error or the fallback's own, since exhaustion then never escapes; that overload comes first. `onExhausted` lives on the per-use options only, and `configureEffect` refuses a `retry` key at the type level as well as at runtime.

Every state type declares `next` as a method signature (`next(result: R): Effect<...>`) rather than a function-typed property, and that is load-bearing under `strictFunctionTypes`. A property's parameter is checked contravariantly, so a `CommandState<never, ...>`, which is what `Command` infers for a function that only throws or returns `Promise.reject(...)`, could not be assigned to `Effect`, whose member is `CommandState<any, ...>`: `any` is not assignable to `never`. Method parameters are checked bivariantly, so the same node is accepted. Nothing is lost, since `Effect` already erases the result type to `any`; what changed is that the throwing Commands in `test/all.js` stopped being type errors under a strict editor. The `tsd` Command section pins a throwing thunk as assignable to `Effect`, directly, under `Retry`, and through `effectPipe`, so a tidy-up that turns the methods back into properties fails the gate.

The recording and replay exports are declared alongside the primitives (`ReplayStep`, `ReplayOutcome`, `Resolver`, `TraceEntry`, `TraceLog`, `RecorderOptions`, `TraceMeta`, `ReplayOptions<Ctx>`, `ParallelDecision`), and `CallConfiguration` types `runEffect`'s third argument as an `EffectConfiguration` plus a boolean `inherit`; the tsd file pins both values, rejects the old string form, and pins that `configureEffect` rejects the key. The tsd file also covers the recording side: `recorder`'s return shape, the `redact` signature with its four-member `kind` union and a fifth rejected, `recordEffect` carrying the flow's error union and checking its `context` against `Ctx`, a `Resolver` returning a wrapped outcome and a bare value rejected, a `Parallel` decision in each valid shape and a cancelled one without its branch rejected, and `timeTravel` returning the bare outcome and refusing a bare entries array. Extend it when touching those types.

### Observability

`examples/opentelemetry-example.js` wires OpenTelemetry spans into `configureEffect`'s hooks: `onRun` opens one span per run, `onStep` a child span per Command, and one per `Parallel` with its branches' Command spans inside it. It is reference code, not part of the library, and it follows the same shape as the recording example: `telemetryHooks(options)` returns a configuration, `enableTelemetry(options)` installs it, and `startTelemetrySdk(options)` stands up an exporter. Nothing happens on import, which is deliberate: the SDK used to start and register a SIGTERM handler at module scope, so merely importing the file opened an exporter and every test run tried to reach `localhost:4318`.

Spans carry names, timings, and status; values belong in a trace. That split is why the example puts no Command input or output on a span: a trace already holds every result keyed by Command name, `redact` strips it before it leaves the process, and what remains can be replayed, whereas a span attribute can be redacted neither after the fact nor before an initial input carrying a password reaches the backend. Removing that recording also removed everything that had to guard it, which is what shrank the file from 94 code lines to 69.

Two constraints in that file are load-bearing. Telemetry must never decide whether business logic runs: the old version called `JSON.stringify(effect.initialInput)` before `pipeline()`, so an input holding a cycle, which any request object or database client has, threw out of `onRun` and left the flow unexecuted while `runEffect` rejected instead of resolving. And `onStep` must `await op()` and return its result, since returning without calling `op` is precisely how replay suppresses I/O, so the same mistake in a tracing hook would silently stop every Command.

`examples/recording-example.js` is the same kind of file for production recording: one recorder per run held in an `AsyncLocalStorage` scope, with `onBeforeCommand` capturing the context so a replay can resolve `Ask`. It stays out of the library for two reasons worth preserving. `node:async_hooks` would be the library's only import and a Node-only one, where `index.js` currently imports nothing and runs anywhere, and the policy it encodes (what to keep, where the sink is, what `redact` strips) belongs to the application. It exports `recordingHooks`, which returns a configuration, plus `enableRecording`, which installs it; the returning form is the composable one, since a self-installing helper would replace hooks the app already set. Both examples are covered by tests, so a change to the hook contract breaks them rather than letting them rot silently, and neither should be edited without running `npm test`.

### Example code in the README

README snippets are code readers copy, and the `README examples` suite runs them: every `js` block is extracted and executed as one program, with the Quick Start's definitions in scope and everything outside the library stubbed, so every `assert` the README prints is a real assertion rather than a claim. Two consequences for editing. A fenced `js` block must be real JavaScript, since the suite parses all of them, so a value shape goes in a `text` block (the retry exhaustion object is the one such block) and a placeholder becomes real code rather than `...`. And a block that needs something new from outside the library needs a stub beside the others in that suite, which is the honest cost of an example that reaches further. The suite was added after the fourth wrong example was found by running the blocks by hand, which is the same argument the library makes about business logic: the check that depends on someone remembering is the one that silently stops happening. A broken example survived review here precisely because it looked right: the flow ended in a bare `saveUser` after a guard that resolved to `Success(true)`, so `db.saveUser(true)` was called, the registration data never reached the database, and the run still reported `Success`. The tree-walking assertions in **Testing Without Mocks** passed the whole time, because a walk checks only which Command comes next and `cmdSaveUser` was still the second call. That was first read as arguments being unobservable, which is wrong and sent the fix into prose: a step's `next` is exactly where the piped value is observable, and `assert.deepEqual(ensureEmailAvailable(input).next(null), Success(input))` fails on that guard. Verified both ways. The section now leads with the per-step assertion and says what each style catches, so the rule is a testing rule first and the shape rules below are what keep the examples matching it. What genuinely cannot be asserted on is the body of a Command's function, since reading the values it closes over means calling it; keep those bodies to a single call.

Two shape rules keep documented pipelines honest, and the Quick Start is written to both:

- **Every step accepts and returns the piped value.** The email guard is a `Command` whose `next` returns `Success(input)` rather than `Success(true)`, so `saveUser` receives the registration data and the pipeline matches the sentence above it. Threading the value through a guard's own continuation costs nothing when the guard is already a Command, which is why no combinator is needed for it.
- **Prefer threading the value over `() => f(outer)`, but do not present it as a rule.** Closing over an outer variable runs correctly in JavaScript and costs nothing there, so the README says so plainly rather than implying breakage. The real cost is TypeScript: a step that ignores its parameter constrains nothing about what produced it, so changing an upstream output from `User` to `string` raises no error in that form and a compile error when a step consumes the value. Documented examples still thread the value, because that is what keeps a typed pipeline checked end to end, and because it reads as data flow. Note that JavaScript examples have no type safety net at all, which is how the `Success(true)` bug shipped: the equivalent TypeScript is rejected with `'boolean' is not assignable to 'User'`.
