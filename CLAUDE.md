# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm test                                          # run all tests
npx mocha test/all.js --grep "pattern"            # run a single test by name
npm run format                                    # Prettier over index.js, index.d.ts, examples/*.js, test/all.js, test/types.test-d.ts, README.md, CLAUDE.md, CHANGELOG.md, CONTRIBUTING.md
npx tsd                                           # type-level gate over test/types.test-d.ts
npx tsc -p jsconfig.json                          # strict tsc over index.js, test/all.js, test/types.test-d.ts, and examples/*.js, reading index.d.ts as a consumer; the same config VS Code uses
npx esbuild index.js --minify --format=esm | gzip -9 | wc -c    # the size the README claims
npx stryker run                                   # mutation testing: mutates index.js, runs test/all.js against each mutant; report in reports/mutation/
```

No build or lint step: the library ships as plain ES modules with no transpilation. Formatting is Prettier, configured in `.prettierrc`; match it when editing. `.github/workflows/ci.yml` runs `npm test` on Node 18 through 24 and, in a second job, Prettier's check; it triggers on pull requests and on pushes to `main`, not on a bare branch push. The size measurement, the two grep rules below, and mutation testing stay manual. Mutation testing is configured in `stryker.config.json` and needs Node 22 or later, which is why it is not in CI, whose matrix starts at 18; on Node 18 and 20 `npm ci` only warns about its engine. A test that passes whatever the code does is invisible to every other check here: three such tests were found by reading, and a mutation run is how the rest are found, so run it after changing `index.js` or its tests. Its survivors are not a to-do list. Most are equivalent mutants that change nothing observable (optional chaining on an `AbortController` that always exists, arrays pre-sized and then filled, `performance.now()` against `Date.now()`, `chain` cases that fall through into identical code, the check after a retry backoff that the loop's own check repeats) or message and narration wording. Two gaps are left on purpose: whether each nested `Parallel` removes its listener from the enclosing signal, which only an internal inspection could test, and the exact wording of `timeTravel`'s narration. A survivor outside those classes is a behaviour no test pins, which is what the run is for. `package.json` has a `files` list, so anything new that must ship in the tarball has to be added there; `npm pack --dry-run` shows what would be published. `CONTRIBUTING.md` restates the rules in this section for a human contributor and points here for the reasons; a new rule goes in both, a new reason only here.

The README's size badge is live: `img.shields.io/bundlejs/size/pure-effect` measures the latest published version with esbuild, the same tool as the command above, so it corrects itself within hours of a publish and reads the previous release's size until then. Bundlephobia's badge was not used because it measures with webpack and terser, so its number differs from the local one, and its Shields integration is often rate limited. The feature bullet also states the size in prose, and that sentence cannot correct itself: re-measure with the command above after adding anything to `index.js` and reword it when the number moves. That bullet is the only place the size is written down. **A commit message and a changelog entry never mention it.** Both are read long after the fact, when the number they quote is stale and the reader has no way to tell; the README bullet is the one copy that gets re-measured, and a second copy in a record nobody re-measures is a copy that goes wrong quietly. Size is also not what either document is for: a changelog answers what changed for a user and a commit message answers why, and neither question is answered by a byte count. Measure it, update the bullet, and leave it out of the history.

The README's `Load Tests` section has the same weakness and nothing that corrects it: it reports experiments run in September 2026 with scripts that are not in this repository, so no check re-measures it. Most of its numbers are counts (requests, spans, traces, runs) that stay true until behaviour changes; the timings go stale with the machine. A change to what the section claims, isolation between concurrent runs, replay fidelity, memory held across runs, or `Parallel`'s limit and ordering, means rerunning an equivalent experiment and updating the section, or cutting the claim. It deliberately carries no size figure, since the feature bullet is the only place the size is written.

**Markdown prose has no hard line breaks.** Write each paragraph and each list item as one line and let the editor soft-wrap; never wrap prose at a column. Hard breaks make later edits reflow whole paragraphs, turning a one-word change into a multi-line diff. `proseWrap: never` enforces this, so `npm run format` unwraps any prose that arrives wrapped. Even so, write it unwrapped in the first place rather than relying on the sweep, since a wrapped paragraph reads as an intended shape until something reflows it. Fenced code blocks are untouched by the setting, and table rows stay one per line; only prose joins.

**No jargon in the README.** A reader meets the library there and should never need vocabulary from functional programming, from the interpreter's internals, or from this file to follow it. What the library exports is not jargon: `Command`, `Retry`, `Parallel`, `Resolver`, `TimeParadox`, `onStep`, `backoff` and the rest are what the things are called, and a reader has to learn them anyway. Everything else gets the plain word. A flow, not an Effect tree. Part of a flow, not a node or a subtree. The Command's function, or `cmd`, not a thunk. Joining, not fan-in. Stops, not short-circuits. A request, not cooperative. Attached, not stamped. Does the same thing again, not deterministic. No catch, not no catch combinator. Runs at the same time, not concurrently, wherever nothing turns on the distinction. `grep -rniE "thunk|combinator|monad|kleisli|effect tree|fan-in|fan-out|short-circuit|cooperative|imperative shell|arity|stamp" README.md` checks a change before it lands and should print nothing. This replaced a rule that banned `thunk` alone, which was the same instinct applied to one word: every other term on that list had already reached the README, and `Independent fan-in` was a section heading. A precise term a reader genuinely benefits from may stay if the plain words follow it in the same breath, which is why `idempotent (safe to run more than once)` survives in the Retry section and is not on the grep list: the gloss is what makes it a definition rather than a gate. That is the exception, not a way around the rule, and a term that needs a gloss every time it appears is a term the README should not be using. The precise words stay available everywhere else, in this file, in JSDoc, in code comments, and in test names, where the reader is a maintainer and precision is worth more than approachability.

**No em dashes.** The `—` character does not appear anywhere in this repository: not in `README.md`, not in this file, not in JSDoc, code comments, test names, or assertion messages. Reach for the punctuation that carries the actual relationship instead of a dash that blurs it. A colon when the second half explains or names the first. Parentheses for an aside the sentence could survive without. A semicolon between two linked independent clauses. A comma for a light pause or a trailing "which" clause. A full stop when the clause can stand on its own, which is usually the honest fix for a dash joining two complete thoughts. Nothing enforces this mechanically, so it is on the author; `grep -rn "—" --include="*.js" --include="*.ts" --include="*.md" .` checks a change before it lands. Table cells that need a "not applicable" placeholder use `n/a`.

**Name a condition when it's used more than once, or when you'd otherwise need a comment to say what it means.** This applies to `index.js`. A concept written inline drifts into spellings that each have to be checked against the others: "a non-null object" was spelled three ways across six places before `isObject` replaced them. A condition one function uses once can be a named `const`, as `cancels` and `haltedByReplay` are. Make a predicate a type guard (`@returns {value is T}`) only where a caller needs the narrowing, as the interpreter loop does with `isPending`: a guard to `object` on a value typed `any` narrows it to `object`, and reading a property off it stops compiling, which is why `isObject` returns a plain `boolean`.

## Design

**pure-effect** is a zero-dependency effect system for JavaScript implementing the "Functional Core, Imperative Shell" pattern. Business logic returns plain data instead of executing side effects, so it can be tested without mocks, and because a flow is inert data until the interpreter walks it, a recorded run can be fed back through the interpreter with no I/O at all. Everything is in `index.js`, and `index.d.ts` declares it.

### Primitives

| Export | Shape | Purpose |
| --- | --- | --- |
| `Success(value)` | `{ type: 'Success', value }` | Wraps a successful result |
| `Failure(error, initialInput)` | `{ type: 'Failure', error, initialInput }` | Stops the pipeline |
| `Command(cmdFn, nextFn, meta)` | `{ type: 'Command', cmd, next, meta }` | Defers a side effect for the interpreter; `meta.name` sets the Command's identity |
| `Ask(nextFn)` | `{ type: 'Ask', next }` | Reads the `context` passed to `runEffect` |
| `Retry(effect, options)` | `{ type: 'Retry', effect, options, next }` | Runs a tree again after an I/O fault; a per-use `onExhausted` runs a fallback when every attempt has failed |
| `Parallel(effects, next?, options?)` | `{ type: 'Parallel', effects, next, options }` | Runs trees at the same time; the first branch to fail cancels the others unless `settled`; `limit` caps how many run at once |
| `effectPipe(...fns)` | n/a | Composes steps into a pipeline through `chain` |
| `runEffect(effect, context, callConfig?)` | async | Runs a flow; a per-call `callConfig` merges over the installed hooks, or replaces them under `inherit: false` |
| `configureEffect(...configs)` | n/a | Adds a layer of process-wide hooks (`onStep`, `onRun`, `onBeforeCommand`) and returns a function that removes it |

`Command`'s `next` is optional and defaults to `(result) => Success(result)`, since most Commands pass their result straight through, and `Parallel`'s defaults to `(values) => Success(values)`. `Parallel`'s second argument is `next` or the options, whichever it looks like, so `Parallel(effects, { limit: 5 })` needs no placeholder; `replayEffect` tells a `Resolver` from a trace by `typeof` the same way. The README's `Composing Larger Flows` section shows the patterns the primitives already support (branching into sub-pipelines, joining `Parallel` results, small local joins that carry a minimal value shaped for their purpose), which is why no combinators were added for them. Its advice against a growing accumulator object is bug avoidance rather than taste: an accumulator hides which step depends on what, lets stale fields outlive the steps that produced them, and widens what carries PII, so keep the examples threading minimal values.

**Command identity** comes from the internal `commandName(eff)`: a non-empty string `meta.name`, else `cmd.name`, else `'anonymous'`. Trace entries are keyed on it, replay matching compares it, and telemetry spans are titled with it, which is why it is one function. `meta.name` exists because `cmd.name` alone made recording depend on syntax: an inline arrow recorded as `'anonymous'`, and a minifier that mangles names renamed every step, both silently. `cmd.name` stays supported and is what the examples use.

### Composition and `initialInput`

`chain` (internal) connects a node to the next pipeline step: `Success` passes its value on, `Failure` stops, and `Command`, `Ask`, `Retry` and `Parallel` wrap their continuations, carrying `Retry`'s `effect` and `Parallel`'s `effects` over untouched. `chain` checks what each step returns, which is the only place the step's name (`fn.name`) is known and so where the useful error message comes from, and it checks `effect == null` before reading `.type`, so a missing return is named rather than thrown as a bare `TypeError`.

Every `Failure` carries `initialInput`, the input of the flow that was called, at any depth, alongside the full error; neither is trimmed, since a test and a developer both need the whole thing. Two mechanisms make that hold, and both are needed. `chain` stamps every node but a `Success` with the pipeline's start, overwriting a sub-pipeline's own, and `effectPipe` ends with an identity pass, `chain(tree, Success, start)`, so the last step's continuations are stamped too; this is what holds for a tree walked by hand in a test. And the interpreter restamps the final `Failure` with the root's input, since the subtrees a `Retry` or `Parallel` holds are run directly rather than reached through a continuation; this is what holds for a run. The outcomes a settled `Parallel` hands `next` never pass that boundary, so each keeps its branch's own input, or none: that input identifies the failed record, and stamping the flow's input onto each would copy a registration's credentials into every one. A `Success` is never stamped, so `assert.deepEqual(result, Success(v))` holds whatever shape the flow had. Only `effectPipe` puts the input on the tree, so a flow whose root is a bare `Command`, `Ask`, `Retry` or `Parallel` carries none and a hook-based recorder records none; the README says to wrap such a flow in a one-step pipeline, since no hook can recover an input that only a closure holds. `recordEffect` takes the input as an argument and does not rely on the stamp.

PII control is split: `redact` is the single mechanism for a trace, and the shell owns what reaches logs, so the guidance is to log `result.error` rather than a whole `Failure`, and to report the `Failure`s a settled `Parallel` hands `next` the same way, since each carries its branch's input.

### The interpreter

`runEffect` is a thin public wrapper over the private `interpret`, which `replayEffect` also calls. Inside it, `execute` walks a subtree in a `while` loop, resolving `Ask` itself and handing every other node to `runRetry`, `runParallel` or `runCommand`. Each returns a `Success` carrying the value for the node's `next`, or the `Failure` or I/O fault that stops the subtree. `onRun` wraps the whole run once, `Retry` attempts included. The loop's condition, `isPending`, reads the type as `value?.type`, so a continuation that returned `undefined` reaches the `EffectTypeError` at the end of `execute` instead of throwing from the condition.

**Three kinds of failure.** This distinction answers a family of bugs, and most of what follows depends on it. A `Failure` a step returned is an **abort**: the flow has decided, and the shell acts on it. A throw from a Command's function is an **I/O fault**, which is what `Retry` exists for. An `EffectTypeError`, a replay fault, or a throw from a continuation or a pure step is a **harness error**, not an outcome, and `runEffect` rejects with it. Without the distinction `Retry` re-ran a lookup whose answer could not change, wrapped a domain error in an exhaustion it had nothing to do with, and let `onExhausted` answer a deliberate abort. An I/O fault is an internal state, `{ type: 'IoFault', error, initialInput }`, which only `execute` and its per-node functions return; it becomes a plain `Failure` wherever it would reach user code, at the `runEffect` boundary and in the outcomes a settled `Parallel` hands `next`. So every `Failure` user code holds is plain data, whatever a step returns is an abort, and a continuation cannot forge a fault, since the loop accepts only the six public types. Keep provenance out of anything user code can hold: it was once a hidden symbol on the `Failure`, and composition kept or dropped it depending on the pipeline's shape. The rule underneath is the README's: a domain outcome is returned, never thrown, so a `cmd` function that throws a business error has told the interpreter it was an I/O fault, and the interpreter acts on that.

**Where a throw comes from.** `runCommand` has two regions, and `next` runs outside both, because a throw means something different in each. A throw from `onBeforeCommand` is an abort, since a veto stops the flow rather than the I/O failing. A throw from the step runner is an I/O fault unless the Command's function had already succeeded: `op` records that, and then the throw is a bug in an `onStep` hook and rejects the run, since retrying would repeat work already done (a telemetry exporter failing after a charge went through once charged the card on every attempt). A hook that throws without calling `op` stays a fault, because that is how replay reports a recorded error and how a circuit breaker written as a hook refuses a call; in a `hooks: true` replay a hook that throws after a replayed step therefore counts as a fault, which is harmless, since nothing executes. `next`, with every pure step it reaches up to the next Command, runs in `execute` after `runCommand` has returned, so a throw there rejects the run, as a throw from any other continuation does. A harness error carries the `harnessError` symbol, always on an `Error` the library created and never on flow data, so both catches rethrow it. `op` is async, so a hook always gets a promise, even for a synchronous function, as the `StepRunner` type and the README's "must `await op()`" promise. The `Where a throw comes from` suite pins each region.

**Malformed flows.** `asEffect` and `effectTypeError` reject anything that is not an Effect with a message naming its source and the likely mistake (`describeValue`): a missing return, `null`, an `async` step, which is named as a Promise and pointed at a Command, a flow passed without its input, or an unrecognised `type`. A malformed flow is a bug and throws; a Command that rejects is a domain outcome. `effectTypeError` attaches a handler to a native `Promise` it reports, so a throwing async step does not crash the process after the caller has caught the error. Only a native `Promise`, because calling `then` on a Knex or Mongoose query builder runs the query.

**Retry.** Options are per-use and merged over `attempts: 3`, `delay: 100`, `backoff: 1`, and `attempts` must be a positive integer. An abort passes through at once, unretried and unwrapped, and `onExhausted` never sees it. An I/O fault is retried, and when attempts run out the result is `{ retryExhausted, lastError, attempts }`, itself an I/O fault so that an enclosing `Retry` retries this one. `onExhausted` runs a fallback Effect under the retry's `f` path prefix: its success feeds `next`, its failure propagates unwrapped, and it never starts in a cancelled branch. Each attempt runs the **entire** wrapped tree again, including Commands that already succeeded, and a Command's `next` is part of that tree, so `Retry(Command(cmd, next))` where `next` continues the flow wraps everything downstream: a booking saga with two such nested retries charged a card nine times. The rule is that a retried Command keeps its default `next` and the branching happens in a later pipeline step, as the README, the JSDoc and the second `Documented sharp edges` test say. Catching and retrying are alternatives: a miss caught inside the `cmd` function and returned as a value is an abort, so a `Retry` around it makes one call and never tries again, and the README says to catch when the flow should handle the outcome as data and to let it throw when `Retry` should act on it.

**Parallel.** Branches run through `runBounded`: `Promise.all` without a `limit`, and a pull-by-index worker pool with one, so results and paths follow array order either way. By default the first branch to fail, or to throw, cancels the others, and its `Failure` is the result, with `next` skipped. Under `settled` a failing branch cancels nothing and `next` receives every branch's outcome as a plain `Success` or `Failure` in array order, while a throw still cancels the others and rejects the run: `settled` catches outcomes that were always possible, not mistakes. `limit` and `settled` are per-use, since they describe the resource and the batch rather than the process, and a limit never reaches a trace, since paths come from array index. The whole `Parallel` is one `onStep` step of type `'Parallel'` whose `op` runs the branches and returns the decision, which branch if any cancelled the others, so the decision is recorded and a replay can hand it back. A hook must call that `op`, and the interpreter rejects with a `TypeError` when a hook returned without letting it run. A branch's throw is held until every branch has settled and rethrown after the step returns, so the decision is recorded and no branch is left running unobserved. `runBranches` picks the rule for whether a settled branch cancels the others (a throw, or a failure unless `settled`, when live; nothing when reproducing a recorded cancellation), hands it to `settleBranches`, and then either checks the recorded decision or builds one from timing. The branch that cancelled the others is tracked apart from the branches that failed because they were cancelled, so a cancellation never displaces the real error.

**Cancellation is a request.** Each `Parallel` has an `AbortController` linked to the enclosing one by `linkedScope`, so cancellation nests. A cancelled branch starts no further Commands: that is checked at the top of `execute`'s loop, again once `onBeforeCommand` returns, since an interceptor such as a rate limiter can wait while a sibling fails (a charge once started 40ms after its branch was cancelled), and again before a `Retry` fallback. A retry backoff ends at once when its branch is cancelled, including one that starts on a signal that has already fired, which is the usual case, since a Command that honours the signal rejects the moment a sibling fails; `delayFor` checks `aborted` first because a listener added to an aborted signal never runs. Stopping the Command already in flight needs its function to pass on the `AbortSignal` it is handed, which is why `cmd` receives the signal inside a `Parallel` and no argument anywhere else. A function that ignores it runs to completion, so a branch's first Command can still write after a sibling has failed, and a pinning test covers that. `Parallel` still awaits every branch before returning. The trigger is the first failure to finish, which is completion order: a synchronous throw beats a promise that rejects a microtask later, whatever their positions, and branches that fail without I/O finish in array order, which is pinned.

### Hooks and `configureEffect`

- `onStep(name, type, op, path)` wraps each Command's execution and each `Parallel`'s branches. It decides whether the Command runs at all, which is how replay suppresses I/O, so a hook that only watches must `await op()` and return its result.
- `onRun(effect, op, flowName)` wraps a whole run, once; `flowName` is `context.flowName`, or `''`.
- `onBeforeCommand(command, context)` runs before each Command, and throwing from it vetoes the Command as an abort.

`configureEffect` is additive. Each call adds one layer and returns a function that removes that layer wherever it sits, idempotently, and several configurations passed to one call form one layer, which is the same as installing them separately. A call with no arguments at all removes every layer, which is how the suites reset; a call whose arguments are all `undefined`, such as `configureEffect(flag ? hooks : undefined)`, is a conditional install that adds and removes nothing. `chainHooks` merges the layers into `globalConfig`, earliest outermost: `onStep` and `onRun` are wrappers that nest, so a thrown Command unwinds from the innermost hook back out, and `onBeforeCommand` interceptors run in order. Keep those semantics if the hook shapes change. A slot no layer defines is absent, and `interpret` picks the library default where it reads the slot. A per-call `callConfig` is merged over the installed wiring by the same merge, innermost, or over nothing under `inherit: false`, and a non-boolean `inherit` throws rather than being coerced. That is why `recordEffect` inside an instrumented application keeps its spans, and why `replayEffect` passes `inherit: hooks`: under `hooks: true` its resolver sits innermost and the configured hooks observe a replay that still executes nothing. Merging is only trustworthy while every nested hook is a watcher, since a global `onStep` that never calls `op` would starve an inner one. Anything that wraps `onStep` passes `path` on as the fourth argument: a wrapper that drops it records a trace without paths, which cannot replay a `Parallel`, and in TypeScript it no longer compiles, since `StepRunner` declares `path` as present. Only the innermost hook can pass `op` an argument, the recorded decision, since `chainHooks` hands outer hooks a closure that takes none; replay's hook is per-call, and so innermost. A leftover `retry` key throws from `configureEffect` and from `callConfig`, checked before any layer is installed; it is migration scaffolding and comes out at 1.0.

`observeSteps(handler)` (internal) is the contract for a hook that only watches: `op` always runs, its result is returned, its error propagates, and anything the observer throws is dropped. It exists because the raw hooks let a throwing `redact` turn a successful run into a `Failure`. Keep it minimal: `recorder` is its only caller and needs only `onStep`. The `durationMs` on each trace entry comes from it, rounded to microseconds.

### Recording and replay (all in `index.js`)

| Export | Purpose |
| --- | --- |
| `recorder(options?)` | Returns `{ onStep, entries, toTrace }`; the `onStep` hook records every Command's result or error, and each `Parallel`'s decision. Options: `redact`, `maxEntries`, `stack` |
| `recordEffect(flowFn, initialInput, opts?)` | Runs a flow for real while recording; returns `{ result, trace }`. Convenience for tests and scripts |
| `replayEffect(effect, traceOrResolver, opts?)` | Replays a tree, feeding recorded outcomes to Commands instead of executing them. Takes a trace or a `Resolver`; returns `{ result, unreached }` for a trace and `{ result }` for a `Resolver`. Options: `context`, `fastRetry`, `hooks`, `onMissing`, `onResolved` |
| `timeTravel(flowFn, traceLog, options?)` | Narrated replay: rebuilds the flow from the recorded input, logs each step, warns on version mismatch and names any unreached steps; returns the bare outcome, since narration is its job |

`fromTrace(traceLog, { onEntry })`, which builds a `Resolver` over the reference trace format and returns it as `{ resolve, missing }`, is **internal**, and `replayEffect` is its only caller. Deliberately not exported: a caller whose traces live in another shape writes a `Resolver` instead, and a caller who only wants to watch a replay uses `onResolved`. The `onEntry` observer is how `replayEffect` learns which entries were handed out; it subtracts those from the trace after the run to produce `unreached`, which is why that field exists for a trace and is absent for a `Resolver`. A step the trace does not hold resolves to `undefined`, as it would from a `Resolver`, so `replayEffect` applies `onMissing` to both, and `missing` describes the step so the refusal still names the path, or the entry number for a trace without paths. It used to throw its own `ReplayError` for a missing step, which `onMissing` never saw, so `'execute'` did nothing for a trace and worked only with a `Resolver`, the one case the tests covered. Two things still win over `'execute'`: a step recorded under another name is a `TimeParadox`, and a missing step that a recorded `Parallel` decision explains is stopped, since production never ran it. Between them those cover every known need, so exporting it would only widen the public surface. The one thing neither covers is _rewriting_ outcomes from a reference-format trace (substituting one step's result, or chaining a fallback), since `onResolved` is an observer whose return value is ignored. Export it again if that comes up; nothing depends on it staying private.

See **Time-travel debugging** below for the invariants these depend on, and the README for each option in full.

### Time-travel debugging

Because a flow is data, a production run can be recorded and replayed later. Recording is just an `onStep` hook, so it needs no change at call sites: install `recorder().onStep` via `configureEffect`, or pass it as per-call config. It merges with tracing whether the two are installed in one call or two. `recordEffect` is the convenience wrapper for tests and scripts.

Seven invariants hold the design together; breaking any of them breaks replay in a way tests may not catch:

- **Replay drives the real interpreter.** `replayEffect` runs the flow through `interpret`, the function behind `runEffect`, rather than walking the tree itself, which is why `Ask`, `Retry`, and `Parallel` replay correctly and why replay semantics cannot drift from execution semantics. The interpreter's only execution point is `await localStepRunner(cmdName, 'Command', op, cmdPath)`, which hands `onStep` a wrapper around the Command's function as `op` instead of calling the function; the wrapper only records whether the function succeeded. Replay's `onStep` never invokes `op` unless `onMissing: 'execute'`, so **no side effect can occur by default**. Preserve that single-execution-point property: a Command executed anywhere else in the interpreter would be invisible to both recording and replay. A `Parallel` also goes through the step runner, but its `op` performs no I/O of its own; it runs the branches, whose Commands each reach the execution point as usual.
- **Path matching, with positional matching for traces that carry no paths.** Every step carries a `path`: its position in the Effect tree, numbered sequentially within a subtree, with each `Parallel` branch and each `Retry` attempt opening its own prefix (`0p1/0r2/0` is branch 1, retry attempt 2, first Command; a retry's `onExhausted` fallback opens `0rf/`). A path depends only on the shape of the tree, never on the order branches finish in, so it is order-independent **and** paradox-detecting at the same time. `fromTrace` matches by path whenever every entry has one. Duplicate paths throw, since a collision would reintroduce the failure paths exist to prevent. A trace whose entries carry no path (recorded before paths existed, or written by hand) is consumed positionally, each entry checked against the Command the flow asks for; exact for sequential flows, and unable to tell `Parallel` branches apart. There is no matching option any more. `strict` used to choose between that positional mode and a per-Command name-queue mode, which was the only way to replay `Parallel` before paths, and **the name-queue mode was the bug paths fixed**: it paired a step with the next recorded entry of the same name, which is completion order, so two `Parallel` branches calling the same Command swapped results whenever replay timing differed from production, and the replay still reported `Success`. Once paths made it unnecessary the option was removed rather than left as a footgun; a `Resolver` remains the way to match by any other rule. The positional resolver refuses a step whose path shows it is inside a `Parallel` (a `p` segment), with a `ReplayError` that says to add paths, because a positional answer there would be right only when the replay happened to finish in production's order, and silently wrong otherwise.

- **The hook contract carries the path as a fourth parameter.** `onStep(name, type, op, path)`. Three-parameter hooks keep working, and `chainHooks` forwards the path through nested wrappers. A hand-rolled wrapper that calls `inner(name, type, op)` without forwarding `path` silently produces a trace with no paths, which then falls back to legacy positional matching: correct for sequential flows, and the old swapping bug for `Parallel`. Forward the fourth argument in anything that wraps `onStep`. In TypeScript such a wrapper no longer compiles, since `StepRunner` declares `path` as present, which it always is; `onRun`'s `flowName` is declared present for the same reason. `CommandInterceptor` is a union of an async and a plain function type rather than one signature returning `Promise<void> | void`: in a JavaScript file a JSDoc `@type` on an async function is its declared signature, and an async function's declared return type has to be a `Promise`, so the single signature broke the reference example's own annotated interceptor under `tsc`. `onStep` also wraps each `Parallel`, with `name` and `type` both `'Parallel'`; its `op` runs the branches, so a hook has to call it, and the interpreter rejects with a `TypeError` when the runner returns without `op` having run rather than continue with no branch results. Only a replay passes `op` an argument, the recorded decision, and only the innermost hook can pass one, since `chainHooks` hands outer hooks a closure that takes none. The replay's hook is per-call and therefore innermost, which is what makes that work.
- **A cancelled `Parallel` replays its recorded decision.** Which branch cancels a `Parallel` is decided by timing, which is exactly the kind of value the README tells users to put inside a Command, and for a while the library broke that rule itself: the decision was never recorded, a replay reached its own decision at replay speed, and a checkout whose charge was declined replayed as the `AbortError` of the stock reservation it had cancelled, because the reservation's single step resolved before the charge branch reached its second. A branch production stopped between steps could also run on in a replay and ask for a step that was never recorded. The decision is now recorded as the `Parallel`'s own entry at its path (`0p`): `{ cancelled: false }`, `{ cancelled: true, branch: i }`, or `branch: null` for a `Parallel` an enclosing one cancelled. A replay of a cancelled `Parallel` reproduces it rather than recomputing it: nothing aborts the scope, each branch runs its recorded steps, a missing step in a branch the decision cancelled is where production stopped it (`fromTrace` throws a `replayCut` marker and the interpreter returns that branch as cancelled), and the result is the recorded branch's failure. If that branch no longer fails, the `Parallel` raises a `TimeParadox`, and so it does when the decision names a branch past the end, which means the shape changed since the recording; falling back to timing there let the first remaining branch the replay reached decide, which is the bug this fixed. A negative branch is never recorded, so it is not a decision and replays by timing like anything else that is not one. Nothing in a replay waits for a cancellation, so a diverged flow cannot hang. A branch whose own code throws is a trigger like a failing one, and its throw is rethrown after the `Parallel`'s step has returned the decision rather than from inside it. Thrown from inside, the step failed, the recorder wrote the error where the decision belonged, and the trace of a run that crashed in a `Parallel`, the one the recording wiring keeps above all, replayed by timing: in the fuzzer's repros the throw vanished behind the failure that had cancelled first, or behind a `ReplayError` for a step production never reached, which `onMissing: 'execute'` then ran live. When reproducing, a throwing branch aborts nothing, since the decision already says where each branch stops, and it re-throws on its own, since its code runs again on the recorded results. Once the throw is fixed, replaying the crash trace is a `TimeParadox`: nothing cancels the other branches any more, so they would run past what the trace holds. A consequence for hooks: a `Parallel`'s `op` returns even when a branch threw, so a hook marks a cancelled one from the decision, as the telemetry example does. A missing step anywhere else is still a `ReplayError`. A trace without decisions, and a Resolver that answers a `'Parallel'` step with anything but a decision, replay by timing as before, and a `'Parallel'` step neither advances `index` nor reaches `onResolved`. Marking each step that finished after its branch was cancelled was considered and rejected: it fixes the declined checkout but not a branch stopped between steps, which leaves no step to mark, nor two branches failing at almost the same moment. The recorder does not `redact` a decision, since it holds no user data and a `redact` that rewrites every result would otherwise destroy it.
- **`fastRetry` exists because retry options are per-use.** A delay is written at the call site and nothing outside the node can override it, since there is no configured retry to override it with. `replayEffect` therefore hands its `fastRetry` to the interpreter, which then waits no time between attempts anywhere in the flow, fallbacks and `Parallel` branches included; without it, replaying a flow that retried in production waits out the production backoff. It waits for no time rather than skipping the wait, so branches replayed by timing interleave as they do with a delay. This replaced `zeroRetryDelays`, a rewrite of the whole tree into copies with `delay: 0`, which had to wrap every continuation to reach every `Retry` and rewrite a fallback later, since that tree does not exist until `onExhausted` runs. That rewrite was replay walking the tree itself, which the first invariant rules out: it had to mirror the interpreter's node types, and a type it missed would have replayed a flow slightly different from the one production ran, with nothing to flag it. Now a replay never touches the flow. It replaces only the interpreter's two ways of reaching outside it, I/O through `onStep` and waiting through `fastRetry`, so the flow it runs is the value production ran, node for node, and in a `hooks: true` replay `onBeforeCommand` and `onRun` receive the flow's own nodes rather than copies. The interpreter already knew it could be replaying, since it reproduces a recorded `Parallel` decision and stops a branch where its recording stops, so the flag adds a setting rather than a new kind of knowledge. It is a parameter of the private `interpret` rather than a key on `runEffect`'s `callConfig` or a fourth argument to `runEffect`, so no public function carries a setting only a replay should use.
- **A replay fault is a harness error, not an outcome.** `effectTypeError` and `replayError` both mark their errors with the `harnessError` symbol, and the interpreter's Command catch rethrows anything carrying it rather than folding it into a `Failure`. That is what keeps a replay fault out of reach of everything that legitimately handles a domain failure: a Command's `next`, `Retry`'s `onExhausted`, and the outcomes a settled `Parallel` collects. Without it the `onMissing` guard was defeated by both of the latter, and a truncated trace replayed as a `Success` whose branches each carried the `ReplayError` as though production had returned it, which is the worst possible answer from a debugging tool. `replayEffect` catches the fault at its own boundary, where nothing downstream can absorb it, and returns the `Failure` this function has always returned, so the public contract is unchanged. A replay fault carries a second mark, `replayFault`, which is how that boundary tells one from an `EffectTypeError`: a malformed flow is a bug in the flow rather than a problem with the trace, so it keeps propagating. A new harness error gets the mark rather than a new name for the interpreter to know about; matching on `name` would have missed `TimeParadox`, which overrides the name `replayError` sets.
- **The outcome wrapper is load-bearing.** A `Resolver` returns `{ result }`, `{ error }`, or `undefined` for "not recorded". The wrapper keeps a Command that legitimately returned `undefined` (`{ result: undefined }`) distinct from having no recording, which is what makes the `onMissing` guard trustworthy. A trace entry needs the same distinction between threw and returned, and for a while had it only in memory: an entry said it threw by having an `error` key, `JSON.stringify` drops a key whose value is `undefined`, and a Command that rejected with no reason, as a callback wrapper's `reject()` does, or whose error `redact` replaced with `undefined`, came back from storage as a step that returned `undefined`. The replay reported `Success` for a run that failed, a `Retry` that ran out of attempts replayed as succeeding at once, and under `onMissing: 'execute'` the next Command ran live. Error entries now carry `threw: true`, which JSON cannot drop. An `error` key without it still reads as a throw, since that is what 0.13 traces and hand-written ones have, so both the flag and the key mark an error and neither is required.

Two further details: `hooks` defaults to `false`, so a replay cannot reach a telemetry backend or a guardrail that performs I/O; and errors cross the trace via `serializeError` / `reviveError` because `message`, `stack`, and `cause` are non-enumerable on `Error` and a plain `JSON.stringify` would silently drop them; `cause` is carried recursively since it is often an `Error` itself. An `AggregateError`'s `errors` is non-enumerable for the same reason and carried the same way, one serialized entry each, because that is where its detail lives: Node's refused connection to `localhost` has an empty message and one entry per address it tried. It travels under its own key, `__errors`, beside the `__error` marker, because a validation error carries an enumerable `errors` as data and revival has to restore each with the enumerability it had; only a non-enumerable array takes that path. Non-`Error` values pass through unchanged, so a Command that rejected with a string still replays as a string. `reviveError` defines `name` and `cause` as non-enumerable own properties, matching where a native Error keeps them, because the README's determinism check is `assert.deepEqual(replayed, result)` and Node compares own enumerable keys: assigning `e.name = ...` made every revived error carry an extra key and the check failed for every `Failure` while passing for every `Success`, which is exactly the half of the check that matters. A subclass instance still revives as a plain `Error` (the trace carries a name, not a prototype), so the check is documented as holding for plain errors.

What replay proves has a boundary worth stating, because the README used to demonstrate only the side of it that works. A replay checks that the flow still asks for the same Commands in the same order and still handles the same answers. It cannot check what the flow computes, since every Command's result comes from the recording rather than from the code under test: change the arithmetic in a pure step, replay the recording of the run that got it wrong, and the next Command is handed the old value straight back, so the replay reports `Success`, returns the pre-fix outcome, and has nothing to flag. Found by recording a refund flow that refunded shipped items, fixing it, and watching the replay report the buggy amount as the fixed flow's answer. Nothing in the library can detect this, and recording arguments would not help either, since the recorded arguments would be the old ones too; the fix is to test a value change against the pure step that computes it and keep replay for the question it answers. The same experiment showed that `unreached` is a proof only when the step that goes away was the last the flow reached: removed from the middle it shifts every later path by one, the replay stops at a `TimeParadox`, and `unreached` then lists what the replay never got to rather than what the fix made unnecessary. `timeTravel` already suppresses its unreached warning after a paradox for that reason; `replayEffect` still returns the list, so the README now says what it means in that case.

Recorded results are snapshotted by the internal `snapshot`, not stored by reference. Without it a later step that mutates a returned object rewrote what the trace said an earlier step returned, and because `toTrace` runs after the flow finishes, the mutation was already baked in by the time a sink serialized it: the trace recorded a value production never saw, and a replay fed that value back. It uses `structuredClone`, or a JSON round trip on a runtime without it, and when that throws, for a value holding a function, it falls back to the internal `copyAround`: arrays and plain objects are rebuilt, everything inside them is copied in turn, and only the parts that cannot be copied, a function or an object holding one, are kept as they are. It does not try JSON after `structuredClone` throws, since a JSON copy would record an uncloneable result without its functions even in memory. The fallback used to be the whole value by reference, which was left as a known gap while its only cost was a Command writing to a context that holds a logger; it stopped being acceptable once redaction was found to share it. Redaction runs on the copy. It used to run first, on the reasoning that nothing sensitive should be cloned before being stripped, but a copy in memory exposes nothing the original does not already hold, and redacting the live value let a redact that deletes a field in place reach the run itself: the result `next` was about to receive, the error the caller would get, the input the Commands close over, and the context `Ask` hands them. An experiment found it with a redact written as `delete value.password`: registration saved users without a password and every correct login failed, but only while recording was installed. A context holding a logger is why the fallback had to change too, since handing `redact` the live context there would have kept the bug for the most common context shape. The value `redact` returns is not copied again: it is built from a copy nothing else holds, and a second clone per step would double the cost of recording for nothing. Replay snapshots again on the way out, in `entryToOutcome`, for the same reason in the other direction: handing the flow the entry's own object let a replayed step that mutates its result rewrite the trace, so replaying one trace twice gave two answers, and a caller mutating a replayed `Failure`'s error did the same. The trace's own `initialInput` and `context` are copied the same way, and when the run starts rather than after it: `toTrace` redacts and copies what it is given at the moment it is called, so `recordEffect` calls it before the run and takes `trace` and `dropped` from a second call afterwards, and the reference wiring does the same in `onRun` and copies the context in its first `onBeforeCommand`. Packaged after the run, a Command that wrote to either rewrote what the trace said production received: an ORM save that assigns the new id to the object it is handed recorded the input with that id, the unchanged flow replayed down the update branch as a `TimeParadox`, and a Command that wrote to the context made the replay take another branch with no paradox at all.

`TraceLog` is the reference trace format, not a contract: `replayEffect` also takes a `Resolver`, so any storage shape works by writing one.

`timeTravel` narrates through `replayEffect`'s `onResolved` hook rather than by wrapping a `Resolver`, which is why it can pass the trace straight through and why `fromTrace` needs no public export. Keep that split: `onResolved` is the seam for _observing_ a replay (logging, counting, step assertions), and a `Resolver` is the seam for _supplying_ outcomes. A throw from `onResolved` stops the replay, and `replayEffect` rejects with the observer's own error. It used to leave the step runner before the recorded result was handed back, so it counted as the Command failing and a `Retry` asked for an attempt production never made. It is not dropped the way `observeSteps` drops a recorder's error, because step assertions are one of the things the seam is for, and a swallowed assertion is a test that cannot fail. The step runner throws a harness-marked stand-in, so nothing in the flow can absorb it, and `replayEffect` rethrows the original at its boundary: marking the observer's error itself would mean mutating the caller's object, and a thrown primitive cannot carry a mark. `timeTravel`'s narration falls back to `String(v)` for a value `JSON.stringify` cannot print, such as a `BigInt` or a cycle, since both can be recorded and narration was failing replays with them. `replayEffect` returns `{ result, unreached }` rather than the bare state, mirroring `recordEffect`'s `{ result, trace }`; `timeTravel` narrates the same list and returns the bare outcome, because narration is its whole job and a caller who wants the entries as data has `replayEffect`. `unreached` exists because a flow that stops issuing Commands early mismatches nothing: no `TimeParadox` fires, the replay ends in `Success`, and the recorded steps it never asked for are the only evidence of the divergence. A regression test for a fix that deliberately skips a step asserts which step; every other recording asserts the list is empty. It rides beside the result rather than on it so the flow's outcome stays exactly what production would have returned, and rather than behind an observer option (which it briefly was) because a value handed to a callback exactly once after completion is a return value in disguise, and the `let unreached` it forced into every test was the tell. It is absent, not empty, for a `Resolver`: an empty list would claim knowledge the replay does not have. `timeTravel` still narrates the list, but not after a `TimeParadox` or `ReplayError`, since the flow never got past the divergence and the error already names it. Narration that reaches for a `Resolver` is a sign the wrong seam is being used.

`redact` therefore has to see everything a trace holds, and for a while it did not. It covered Command results only, so a caller who installed a correct redact still shipped `initialInput` verbatim, the `context` verbatim, and any custom property on a thrown error: in the registration flow that is the plaintext password in two places and the auth token in a third. It now receives results, serialized errors, and the trace's own `initialInput` and `context`, with a `kind` argument of `'result'`, `'error'`, `'initialInput'`, or `'context'` to tell them apart. Keep that coverage complete if the trace format grows another field, since a field redact cannot see is a field that leaks. An absent `initialInput` or `context` is left `undefined` rather than passed through, so a redact that spreads its argument cannot turn nothing into an empty object.

### TypeScript

Full generic type declarations are in `index.d.ts` and referenced via the `types` field in `package.json`. Type-level tests live in `test/types.test-d.ts` and run via `tsd` as part of `npm test`.

`index.d.ts` is hand-maintained beside `index.js`, so the two can drift. Three mechanisms guard the drift: the `Declaration parity` test pins the export lists to each other in both directions; `tsd` checks the declarations against `test/types.test-d.ts`; and `npm test` runs `tsc -p jsconfig.json`, strict `checkJs` over `index.js`, `test/all.js`, and `examples/*.js`. That last leg reads the declarations too, not only the JSDoc: `test/all.js` imports `../index.js`, and TypeScript resolves that to the sibling `index.d.ts` before it considers the JavaScript, so the test suite is checked as a strict consumer of the public types. The leg was added after a narrowing error in the interpreter shipped through a green gate and was found in an editor, the second time a lens existed but was not in the gate. It then had to be widened twice for the same reason. The config listed `index.js` alone while `test/all.js` opened with `// @ts-check` and was annotated to typecheck, so an editor showed errors there that the gate never saw. And it ran without `strict`, while VS Code checks JavaScript with `strictNullChecks` and `strictFunctionTypes` by default and consults only `tsconfig.json` or `jsconfig.json`, so it ignored the old `tsconfig.check.json` and reported errors against a green gate. The file is named `jsconfig.json` and is strict precisely so that the editor and the gate read one configuration; keep both properties, and add any checked JavaScript that lives in this repo to its `include` list. `test/types.test-d.ts` is in the list too, which is possible only because its deliberate errors are `@ts-expect-error` directives rather than `expectError` calls (see below). **Check `npm test` by exit code.** `tsd` failures print neither "passing" nor "failing", so piping the output through `grep -E "passing|failing"` hides them entirely, which is how `runEffect`'s declaration stayed deleted through several edits here while every other check reported green. It was removed as collateral by a slice that targeted an adjacent block, so after any structural edit to `index.d.ts`, compare the runtime exports against the declared ones rather than trusting the diff.

Deliberate type errors in `test/types.test-d.ts` are written as `// @ts-expect-error` directives, never as `tsd`'s `expectError(...)`. Both assert that the next expression fails to typecheck, but only the directive is understood by the compiler itself: `expectError` leaves a real diagnostic in the file that `tsd` swallows and every other tool reports, so with it the file showed ten red lines in VS Code and could not be part of the `tsc` gate, which is how a green `tsd` and a red editor coexisted for a while. With the directive, TypeScript suppresses the error and reports `Unused '@ts-expect-error' directive` if it ever stops occurring, and `tsd` fails on that diagnostic, so the assertion is as strong as before (verified by making a suppressed line valid and watching `tsd` fail). What is given up is `expectError`'s check that the error is one of a few specific codes: a directive is satisfied by any error on the line, so keep each suppressed expression small enough that only the intended mistake can fail it, and give every directive a reason. The directive covers exactly one line, so a suppressed expression stays on one line.

`Effect<T, E, Ctx>` carries three type parameters: value type, error union, and context type. `Ctx` flows through `AskState`, `CommandState`, `RetryState`, and `ParallelState`. `Ask<T, E, Ctx>` types the context callback parameter. Each `effectPipe` step has its own context type, `C1` to `Cn`, and the pipeline's is their intersection. A single shared `Ctx` was inferred as `unknown` whenever any step declared none, since `unknown` is a supertype of every candidate, so a validation step ahead of an `Ask` lookup, which is the README's own shape, switched context checking off for the whole pipeline and a wrong context compiled; `unknown & AppCtx` is `AppCtx`, so a step that reads no context costs nothing. `runEffect` and `recordEffect` take the context through a conditional rest parameter: optional when the flow's context type is `unknown`, required otherwise, since the runtime hands `Ask` an empty object when none is passed. `Ctx` defaults to `unknown` so existing code without context typing is unaffected.

Error unions need explicit return annotations. A step written as `(i: User): Effect<User, 'taken'> => ...` contributes `'taken'` to the pipeline's union, but the same step left to inference from a bare `Success(x) | Failure(y)` return type yields `E = unknown`, and one `unknown` absorbs every other member of the union, so `result.error` degrades to `unknown` for the whole pipeline. Annotate `Effect<T, E>` on any step whose error type is meant to survive, and write type-level examples that way.

`effectPipe` is declared as 20 overloads, one per pipeline length, the same ceiling as Effect-TS's `pipe`; it was 8 until a nine-step pipeline, written to test the limit, failed to compile with `Expected 1-8 arguments`. Nothing in this repository comes close: the longest pipeline in the README, the tests, and the examples has four steps. The overloads are generated in one shape, numbered values `T0` to `Tn`, then errors `E1` to `En`, then contexts `C1` to `Cn`, so extending the ceiling means regenerating the block in that shape rather than editing one overload by hand; no caller passes these type parameters explicitly, which is what made renaming them from letters free. Two alternatives were rejected. A single variadic signature built from recursive types removes the ceiling, but an inline step with no annotation loses the parameter type it is inferred from the previous step, and its errors are far harder to read. A catch-all overload past the ceiling that accepts any length untyped is worse, because a long pipeline would silently stop being checked while looking typed; a compile error at 21, with nesting as the workaround, is the honest failure. The tsd file pins 9 and 20 steps, including an unannotated inline last step, the full error union, and the context, plus 21 rejected and the nested form accepted.

`Retry`'s declared error is `E | RetryExhaustedError`, and both halves are deliberate. An abort the wrapped tree returns leaves unretried and unwrapped, so its `E` escapes as it is; an I/O fault the loop cannot get past becomes `{ retryExhausted, lastError, attempts }`, and `lastError` is `unknown`, because what reaches it is only ever a thrown value (a Command's function throwing, or a nested `Retry` running out) and nothing declares what a function throws. It was `RetryExhaustedError<E>` with `lastError: E` until aborts stopped being retried, after which `E` could never reach `lastError` and `const e: 'flaky' = result.error.lastError` compiled against a runtime `Error`. The type parameter stays, defaulting to `unknown` and never filled in by `Retry`, because a caller who knows what their function throws annotates with it, as `test/all.js` does with `RetryExhaustedError<Error>`; the tsd file pins that the abort type is refused as `lastError`. `RetryState`'s `effect` field is typed `Effect<T, any, Ctx>` because the node's error is declared on the node itself rather than read off the wrapped tree. The declaration once claimed `E` alone, which made `result.error` lie for every exhausted `Retry`, and then `RetryExhaustedError<E>` alone, which stopped being true when aborts stopped being retried; the tsd assertions in the Retry section pin the current shape. With a per-use `onExhausted` the declared error is `E | E2`, the abort's error or the fallback's own, since exhaustion then never escapes; that overload comes first. `onExhausted` lives on the per-use options only, and `configureEffect` refuses a `retry` key at the type level as well as at runtime.

Every state type declares `next` as a method signature (`next(result: R): Effect<...>`) rather than a function-typed property, and that is load-bearing under `strictFunctionTypes`. A property's parameter is checked contravariantly, so a `CommandState<never, ...>`, which is what `Command` infers for a function that only throws or returns `Promise.reject(...)`, could not be assigned to `Effect`, whose member is `CommandState<any, ...>`: `any` is not assignable to `never`. Method parameters are checked bivariantly, so the same node is accepted. Nothing is lost, since `Effect` already erases the result type to `any`; what changed is that the throwing Commands in `test/all.js` stopped being type errors under a strict editor. The `tsd` Command section pins a throwing thunk as assignable to `Effect`, directly, under `Retry`, and through `effectPipe`, so a tidy-up that turns the methods back into properties fails the gate.

Three declarations exist to steer inference, and each came from a real failure. The non-settled `Parallel` overloads accept only `settled?: false`, because a `settled` known only as a `boolean`, from a shared options object or a caller's `ParallelOptions`, matched the overload that types `next` as the values while the runtime handed it outcomes; refusing it costs an options variable typed `ParallelOptions` for its `limit` alone, which has to be typed narrower. `Command` has a first overload for the default `next`, whose value type is the function's result, because with only the general signature a `Command(fn)` inside a step annotated with its return type had its value type inferred from the annotation, as `unknown`, and `Retry(Command(fn))` failed to compile in exactly the shape the README recommends. And `redact`'s value is `any` rather than `unknown`, since every redact spreads or reads it and the README's own examples did not compile. `version` accepts `undefined` explicitly for `exactOptionalPropertyTypes`; `tsd` runs without that flag, so that one was verified by hand and is not pinned. `Parallel` still infers no error type from its branches, deliberately left: the declared union already misses thrown errors, so a `switch` over it needs a fallback anyway, and `unknown` there costs narrowing rather than safety.

The recording and replay exports are declared alongside the primitives (`ReplayStep`, `ReplayOutcome`, `Resolver`, `TraceEntry`, `TraceLog`, `RecorderOptions`, `TraceMeta`, `ReplayOptions<Ctx>`, `ParallelDecision`), and `CallConfiguration` types `runEffect`'s third argument as an `EffectConfiguration` plus a boolean `inherit`; the tsd file pins both values, rejects the old string form, and pins that `configureEffect` rejects the key. The tsd file also covers the recording side: `recorder`'s return shape, the `redact` signature with its four-member `kind` union and a fifth rejected, `recordEffect` carrying the flow's error union and checking its `context` against `Ctx`, a `Resolver` returning a wrapped outcome and a bare value rejected, a `Parallel` decision in each valid shape and a cancelled one without its branch rejected, and `timeTravel` returning the bare outcome and refusing a bare entries array. Extend it when touching those types.

### Observability

`examples/opentelemetry-example.js` wires OpenTelemetry spans into `configureEffect`'s hooks: `onRun` opens one span per run, `onStep` a child span per Command, and one per `Parallel` with its branches' Command spans inside it. It is reference code, not part of the library, and it follows the same shape as the recording example: `telemetryHooks(options)` returns a configuration, `enableTelemetry(options)` installs it, and `startTelemetrySdk(options)` stands up an exporter. Nothing happens on import, which is deliberate: the SDK used to start and register a SIGTERM handler at module scope, so merely importing the file opened an exporter and every test run tried to reach `localhost:4318`.

Spans carry names, timings, and status; values belong in a trace. That split is why the example puts no Command input or output on a span: a trace already holds every result keyed by Command name, `redact` strips it before it leaves the process, and what remains can be replayed, whereas a span attribute can be redacted neither after the fact nor before an initial input carrying a password reaches the backend. Removing that recording also removed everything that had to guard it, which is what shrank the file from 94 code lines to 69.

Two constraints in that file are load-bearing. Telemetry must never decide whether business logic runs: the old version called `JSON.stringify(effect.initialInput)` before `pipeline()`, so an input holding a cycle, which any request object or database client has, threw out of `onRun` and left the flow unexecuted while `runEffect` rejected instead of resolving. And `onStep` must `await op()` and return its result, since returning without calling `op` is precisely how replay suppresses I/O, so the same mistake in a tracing hook would silently stop every Command.

`examples/recording-example.js` is the same kind of file for production recording: one recorder per run held in an `AsyncLocalStorage` scope, with `onBeforeCommand` capturing the context so a replay can resolve `Ask`. It stays out of the library for two reasons worth preserving. `node:async_hooks` would be the library's only import and a Node-only one, where `index.js` currently imports nothing and runs anywhere, and the policy it encodes (what to keep, where the sink is, what `redact` strips) belongs to the application. Its `onRun` reports an error from `keep` or the sink to `onSinkError`, defaulting to `console.error`, rather than let it replace the run's outcome: the README's own sink calls `JSON.stringify`, which throws on a circular value such as an HTTP client's error, and the run used to reject with that instead of its own `Failure`. A run that rejects because the flow's own code threw is offered to `keep` as a `Failure` carrying the thrown error, sent to the sink, and then rethrown. Once 0.14 made such a throw reject the run instead of returning a `Failure`, the rejection skipped the sink entirely, so the runs most worth replaying, a `TypeError` in a pure step after an API changed shape, left no trace even though the recorder held the entry that reproduces the crash. `recordEffect` still rejects without its trace, since in a test or a script the error is already in front of the caller. It is the same rule as the telemetry example's, that observing a run never decides it. It exports `recordingHooks`, which returns a configuration, plus `enableRecording`, which installs it; the returning form is the composable one, since a self-installing helper would replace hooks the app already set. Both examples are covered by tests, so a change to the hook contract breaks them rather than letting them rot silently, and neither should be edited without running `npm test`.

## Settled decisions

Each of these was weighed and decided. Do not propose them again as improvements or rank them as weaknesses; the reasons are here.

- **No generator syntax.** A generator-based flow would yield the same Command objects, but a generator is used up as it runs, while a flow built from Commands and `next` continuations is a reusable value: a test calls `step.next(null)` and `step.next({ id: 1 })` on the same node to explore both branches, `chain` wraps a sub-pipeline it did not build, and the `Kleisli laws` suite holds because continuations compose. Neither form lets a reader see past the next Command without supplying an answer, so inspection is not the difference; reusability is. The nesting that dependent values cost is the price, and the `Composing Larger Flows` patterns keep it low.
- **No catch.** An `Attempt` node was designed and rejected: catch brings non-local control flow into a design whose point is explicit data flow, and every motivating case but one was already expressible, as the README's `Which Errors Are Data` section shows (an outcome the flow handles is data that a `next` branches on, and `Failure` means abort). The exception, recovering from `Retry` exhaustion inside the flow, became `Retry`'s per-use `onExhausted`, for three reasons: it had no in-library expression, since the workaround split one operation across two runs and two traces; retry-then-fallback is a standard resilience pairing (Polly, resilience4j), so the demand was predictable; and it completes `Retry`'s own failure handling rather than adding catch. The ceiling stands: no general catch, only an I/O fault is recoverable (from anywhere in the wrapped tree, deliberately), `onExhausted` is per-use, and a cancelled branch skips it.
- **`attempts: 0` throws.** A `Retry` that does not retry is not a `Retry`, and `0` was the one spelling that made `onExhausted` a catch at no cost. `attempts: 1` still recovers from any I/O fault, but at the visible cost of running the tree twice. A companion option was dropped for the same reason, since `settled` already isolates a batch branch.
- **No global retry options.** How a dependency misbehaves is a property of that dependency, not of the process, and a shared `const flakyNetwork = { attempts: 3, backoff: 2 }` passed to each `Retry` covers the repeated case where anyone reading the flow can see it. A `retry` key throws rather than being ignored, since ignoring it would quietly turn a configured `attempts: 5` back into 3.
- **`settled` hands `next` `Success` and `Failure` nodes**, not `Promise.allSettled`'s `{ status, value }`, since the library already has a vocabulary for succeeded or failed. It exists because a batch of independent records was the one shape nothing could express: one bad record cancelled the rest mid-flow, which in a billing job meant a charge with no invoice.
- **A `Parallel`'s trigger is the first failure to finish**, not the first by array order. Either is a true answer, and a replay returns the recorded one. The docs once promised array order and were corrected rather than the code.
- **No `AbortSignal` for a whole run**, and none reaches a Command outside a `Parallel`: most flows are a few quick Commands, and a caller that needs one puts a signal in the context. A signal read that way makes the function throw, which is an I/O fault, so a `Retry` around it retries and then runs `onExhausted`, and the run can report the fallback's `Success` after the caller cancelled; inside a `Parallel` the interpreter checks its own signal and skips both.
- **No finalizer inside a flow.** Cleanup for a run, a transaction included, is a try/finally around `runEffect` in the shell.
- **Recursing through `effectPipe` is quadratic, and that is left alone.** `poll = (n) => effectPipe(fetch, (s) => (s.done ? Success(s) : poll(n - 1)))(n)` wraps one more continuation per level and overflowed the stack at 20,000 levels; the same loop recursing through a Command's `next` stays linear. Loops that long are rare, so a docs note that loops go through `next` is the most it warrants.
- **Nested pipelines for dependent values are a TypeScript cost only.** In JavaScript a step can close over anything in scope; threading the value is what keeps a typed pipeline checked.
- **A `TimeParadox` after a flow changes shape is the design.** A trace belongs to the version of the flow that recorded it, nothing resumes a recorded run against newer code, and matching loose enough to survive an inserted step would have to guess. An incident test is re-recorded when its flow changes shape.
- **A trace records results, never Command arguments.** Given `initialInput` and the recorded results the flow runs the same way again, so replaying to a step rebuilds its arguments. A guardrail vetoes on the context or on `meta`, which `onBeforeCommand` receives; a cache hook would need `meta` handed to `onStep`, not recorded arguments, and nothing has needed one. Recording arguments would double a trace's PII surface for no replay benefit, since arguments are usually the sensitive half of a call.
- **A trace keeps data, not objects.** `structuredClone` drops classes and a JSON sink loses more, such as `Date` and `Map`. Keeping references to class instances brings back the mutation bug for the values most often mutated, ORM entities, and cannot survive JSON anyway; a tagged value encoding with per-class codecs is more machinery than the problem warrants. Commands return plain data instead, as the README says.
- **Steps match by path, with no option to choose.** A `strict` option once chose between positional matching and a per-name queue, and the queue was the bug paths fixed: it paired a step with the next entry of the same name, which is completion order, so two `Parallel` branches calling one Command swapped results whenever the replay finished in a different order. It was removed rather than left as a trap; a `Resolver` matches by any other rule. Marking each step that finished after its branch was cancelled was rejected too: it fixes one case and leaves a branch stopped between steps with no step to mark.
- **`fastRetry` is a parameter of the interpreter**, not a rewrite of the tree. `zeroRetryDelays` rewrote the tree into copies with `delay: 0`, which was replay walking the tree itself: it had to mirror the interpreter's node types, and a type it missed would have replayed a slightly different flow with nothing to flag it. The interpreter already knows it may be replaying, since it reproduces recorded decisions and stops branches at a replay cut, so the flag adds a setting rather than a kind of knowledge. It lives on the private `interpret`, not on `runEffect`'s `callConfig` or as a fourth argument, so no public function carries a setting only a replay should use.
- **Per-call configuration merges; it never replaces one slot.** `inherit` is a boolean: merge over the installed wiring by default, over nothing when `false`. Replacing a single slot was dropped because it caused a real bug (`recordEffect` inside an instrumented application produced runs with no spans), because it means something only when you know what the other slots hold, and because nothing but replay needed it. The name was chosen over `global`, Node's alias for `globalThis`, and `ambient`, a new noun. `configureEffect`'s layers replaced a one-slot rule under which a later install displaced the earlier wiring and a late restore could discard another caller's hooks.
- **What is internal stays internal.** `fromTrace` is not exported: a caller with traces in another shape writes a `Resolver`, and one who only wants to watch uses `onResolved`; export it again if rewriting outcomes from a reference trace comes up, since `onResolved`'s return value is ignored. `observeSteps` was briefly exported as `observe` and removed, since it cost 270 bytes for one internal caller and no consumer, the same argument that removed `tap`. `chainHooks` was briefly exported and folded into `configureEffect`, since a merge is only useful on the way into a configuration.
- **The conveniences stay.** `recordEffect` and `timeTravel` own the trace metadata. `timeTravel` could be rebuilt from `onResolved` in ten lines, but the one-line form is what makes the feature graspable.
- **Recording stays out of the library.** `node:async_hooks` would be `index.js`'s only import, and a Node-only one, and the policy the reference wiring encodes (what to keep, where the sink is, what `redact` strips) belongs to the application.
- **`effectPipe` stops at 20 steps.** A single variadic signature built from recursive types loses the parameter type an unannotated inline step infers from the step before, and its errors are far harder to read; a catch-all overload past 20 would silently stop checking a long pipeline while it looked typed. A compile error at 21, with nesting as the workaround, is the honest failure.
- **`index.js` stays one file.** Splitting it by concern would mean going back and forth between files to follow one path, such as a Command from the interpreter through a hook into the recorder, which costs a reader more than a long file does.
- **`runBranches` runs both modes through `settleBranches`.** It once held two algorithms, running live and reproducing a recorded cancellation, with a `reproducing` flag checked in three places. Now `settleBranches` takes the one thing the modes differ in, the rule for whether a settled branch cancels the others, and `runBranches` reads the mode in two places a few lines apart. Splitting the modes into `decideByTiming` and `reproduceCancellation` was tried and folded back: following one `Parallel` went through seven functions, with the same four arguments handed down unchanged.
- **Sharp edges are documented, not guarded.** `Retry` repeating its whole wrapped tree, and a `Parallel` branch whose Command ignores its signal running to completion, are pinned by the `Documented sharp edges` suite and each has a README Limitations entry; a guard would have to ban legitimate trees, since the hazard is not visible in the data. If `Retry` is ever changed to resume rather than repeat, that suite is the one to read first.

## Tests

`test/all.js` holds every runtime test, with a user-registration domain as the running example. `registerUserFlow` has the same shape as the README's Quick Start, so the tests and the documentation demonstrate one idiom. The test names say what each suite covers; these are the conventions they follow.

- **Assert on the returned data**, such as Commands, Failures and traces, rather than on side effects. That is the usage pattern the library exists for.
- **Reset the hooks in every suite** with `beforeEach(() => configureEffect())`, a bare call. Hooks are process-wide and outlive a suite, and `configureEffect({})` adds an empty layer rather than resetting: suites guarded that way once ran under whatever the previous suite had installed, and stayed green only because the leaked hooks wrote to arrays nobody read. The first suite resets too, since being declared first is luck rather than isolation.
- **Count I/O in replay tests.** Their Commands count their own invocations, so a test can assert that a replay performed none, and a replay is checked from memory and from JSON.
- **Test behaviour through the public surface.** Composition such as `configureEffect merging` and `Per-call inherit` is checked by what runs rather than by inspecting a merged object, and an internal such as `observeSteps` is reached through its only public consumer.
- **Anchor an equation to a value.** The `Kleisli laws` suite checks the laws by running both sides, and since a `chain` that dropped every continuation would satisfy them with both sides equally broken, it also anchors one composition to the value and I/O computed by hand.
- **Each example file has a suite**, so a change to the hook contract breaks the examples rather than letting them rot. The telemetry suite injects a stub through the example's `tracer` option, which is why that option exists.
- **Audit the guidance when behaviour changes.** Write the flow a careful reader would write after reading each documented sharp edge, and run it: twice the code here moved and the README's advice did not move with it.

`test/types.test-d.ts` holds the type-level tests, run by `tsd`; its deliberate errors are `@ts-expect-error` directives, for the reason under TypeScript.

### Example code in the README

README snippets are code readers copy, and the `README examples` suite runs them: every `js` block is extracted and executed as one program, with the Quick Start's definitions in scope and everything outside the library stubbed, so every `assert` the README prints is a real assertion rather than a claim. Two consequences for editing. A fenced `js` block must be real JavaScript, since the suite parses all of them, so a value shape goes in a `text` block (the retry exhaustion object is the one such block) and a placeholder becomes real code rather than `...`. And a block that needs something new from outside the library needs a stub beside the others in that suite, which is the honest cost of an example that reaches further. The suite was added after the fourth wrong example was found by running the blocks by hand, which is the same argument the library makes about business logic: the check that depends on someone remembering is the one that silently stops happening. A broken example survived review here precisely because it looked right: the flow ended in a bare `saveUser` after a guard that resolved to `Success(true)`, so `db.saveUser(true)` was called, the registration data never reached the database, and the run still reported `Success`. The tree-walking assertions in **Testing Without Mocks** passed the whole time, because a walk checks only which Command comes next and `cmdSaveUser` was still the second call. That was first read as arguments being unobservable, which is wrong and sent the fix into prose: a step's `next` is exactly where the piped value is observable, and `assert.deepEqual(ensureEmailAvailable(input).next(null), Success(input))` fails on that guard. Verified both ways. The section now leads with the per-step assertion and says what each style catches, so the rule is a testing rule first and the shape rules below are what keep the examples matching it. What genuinely cannot be asserted on is the body of a Command's function, since reading the values it closes over means calling it; keep those bodies to a single call.

Two shape rules keep documented pipelines honest, and the Quick Start is written to both:

- **Every step accepts and returns the piped value.** The email guard is a `Command` whose `next` returns `Success(input)` rather than `Success(true)`, so `saveUser` receives the registration data and the pipeline matches the sentence above it. Threading the value through a guard's own continuation costs nothing when the guard is already a Command, which is why no combinator is needed for it.
- **Prefer threading the value over `() => f(outer)`, but do not present it as a rule.** Closing over an outer variable runs correctly in JavaScript and costs nothing there, so the README says so plainly rather than implying breakage. The real cost is TypeScript: a step that ignores its parameter constrains nothing about what produced it, so changing an upstream output from `User` to `string` raises no error in that form and a compile error when a step consumes the value. Documented examples still thread the value, because that is what keeps a typed pipeline checked end to end, and because it reads as data flow. Note that JavaScript examples have no type safety net at all, which is how the `Success(true)` bug shipped: the equivalent TypeScript is rejected with `'boolean' is not assignable to 'User'`.
