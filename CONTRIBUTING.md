# Contributing

Thanks for taking the time. These are the rules a change has to follow.

## Before opening a pull request

- **Read the matching section of `DESIGN.md` before changing how something works.** It records why each part works as it does, what broke before it did, and the designs already weighed and dropped. A change that settles a design question adds its reason there.
- **Run `npm test` and check its exit code.** It runs mocha, `tsd`, and strict `tsc` in sequence. A `tsd` failure prints neither "passing" nor "failing", so a glance at the output can miss it; a non-zero exit cannot.
- **Run `npm run format`.** Prettier covers the source, the tests, the examples, the scripts, and the Markdown. Prose in Markdown is written as one line per paragraph or list item, never wrapped at a column.
- **Name a condition in `index.js` when it's used more than once, or when you'd otherwise need a comment to say what it means.** Use a predicate defined beside its first use, or a named `const` when one function uses it once.
- **Keep comments in `index.js` short and about the present.** A comment says what the code does now and why, in a sentence or two. The bug a line fixed, and the full case for a choice, go in `DESIGN.md`; a comment does not recount an incident or restate the line below it.
- **Check an argument through the shared check that covers it.** Options go through `checkOptions`, with a rule for every option the function reads, a trace through `checkTrace`, and a function that builds a flow through `checkFlowFn`. A check written inside one function drifts from the others: the options argument itself, a trace's entries and the flow function each went unchecked somewhere until the checks were shared.
- **Put a new definition in the section of `index.js` it serves.** That is usually the section that calls it. The contents comment at the top of the file lists the sections, so update it when a section gains or loses something it names. Where two sections share a private protocol, as replay and the interpreter do, the comment at each end names the function at the other.
- **Run `npm run test:fuzz` after changing the interpreter, replay or `effectGen`.** It runs seeded random flows both as pipelines and with generator flows mixed in, many more than `npm test` does, and CI runs it too. A failure prints the seed and the command that reruns it; turn that flow into a test in the file for its concern.
- **Keep generator flows made of ordinary nodes.** `effectGen` builds its flows through `chain`, and a node never carries an iterator or a proxy, so tests, traces and hooks see the same data as for a pipeline. A step that stops a generator flow runs its `catch` and `finally`, and anything that would let the body recover from it is refused with an `EffectTypeError` rather than a warning.
- **Mark only the public declarations in `index.d.ts` with `export`.** The file ends with `export {}`, which keeps everything unmarked private, so a helper type stays unmarked rather than becoming API by accident.
- **Keep `index.d.ts` in step with `index.js`.** The declarations are hand-maintained, so a new or changed export needs both files; the `Declaration parity` test fails when the two lists differ. A new type needs an assertion in `test/types.test-d.ts`, with deliberate errors written as `// @ts-expect-error` directives rather than `expectError` calls.
- **Change `effectPipe`'s overloads in `scripts/effect-pipe-overloads.js`, not in `index.d.ts`.** Run `npm run generate` to rewrite them; a test fails when the file and the script disagree.
- **Change the rules in the README's Rules section, and the task index in `scripts/rules-file.js`, not in `RULES.md`.** Run `npm run generate` to rewrite it; a test fails when the file and the script disagree, or when one of its links names a heading the README lacks.
- **Keep `index.d.ts` compiling on TypeScript 5.1.** `npm run test:ts-minimum` compiles the declarations and the type tests with it, and CI runs it too. It is not part of `npm test`, and it fetches TypeScript 5.1 with `npx` the first time.
- **Declare an optional option or hook field as `T | undefined`.** An option or hook set to `undefined` keeps its default, and a project compiled with `exactOptionalPropertyTypes` cannot pass a value read from configuration, typed `T | undefined`, to a field declared `T`. `tsd` runs with that flag, so give a new option a line in the type tests' section on options set to `undefined`. A test compiles each example under the flag too, since users copy the examples into their own projects.
- **Keep jargon out of the README and `REFERENCE.md`.** The names the library exports are fine; everything else gets the plain word, so a flow rather than an Effect tree, joining rather than fan-in, stops rather than short-circuits, and a returned `Failure` stops a flow rather than aborting it. A term the README coins, such as walking a flow, is defined where it first appears. A precise term may stay where the plain words follow it in the same breath.
- **Keep the examples in the README and `REFERENCE.md` runnable.** The `README examples` suite executes every `js` block in both files with its assertions live, so a fenced `js` block has to be real JavaScript: put a value shape in a `text` block, write out a placeholder rather than `...`, and add a stub to that suite for anything new an example reaches for outside the library. The `README TypeScript examples` suite compiles each README `ts` block in a strict project, so a `ts` block has to be real TypeScript as well, with a stub under its heading in that suite for anything it reaches for outside the library.
- **Teach in the README, and state each rule in `REFERENCE.md`.** A guide section explains how a feature works, with an example, and ends with a link to its rules. `REFERENCE.md` holds the API, one line per option, parameter or rule, and every exact rule and edge case, by feature, each stated once; the Rules list, Limitations and a guide's advice only summarise it and link.
- **Keep the README's orientation sections short.** The Core and the others are a few plain sentences. Where something is missing, add a sentence or two rather than restructuring the section.
- **Add a changelog entry** under `Unreleased` in `CHANGELOG.md` for a change to what the library does or exports, placed by importance within its section: a breaking change before the rest, then what affects the most users or changes what their runs do. Keep it short and plain: a sentence saying what changed, and at most one more short sentence on what a user must do, with no bold except a label such as `Breaking:`; the story of a fix goes in `DESIGN.md`. A documentation-only change gets no entry, unless it adds a file the package ships, as `RULES.md` did, and a commit message does not list the docs updated alongside a code change.
- **Write each commit message as one short line,** with no body.
- **Call the library Pure Effect in prose.** `pure-effect` is its package name, written as code where code needs it: an import, `npm install`, `package.json`, a URL.

## What to know about the tests

The runtime tests are in `test/`, a file for each concern (`core`, `retry`, `parallel`, `hooks`, `recording`, `replay`, `gen`, `fuzz`, `examples` and `docs`). Put a new test in the file for its concern, and anything two files need in `test/helpers.js`.

Tests assert on the data structures a flow returns rather than on side effects; that is the usage pattern the library exists for, so keep it. Hooks installed with `configureEffect` are process-wide and outlive a suite, so every `describe` that could inherit another's wiring resets with `beforeEach`. Both files in `examples/` are covered by tests and should not be edited without running them.

## Reporting a bug

Open an issue with the smallest flow that reproduces it. If replay is involved, the trace and the flow together are usually enough to reproduce the problem with no I/O at all, which is the point of the library; strip anything sensitive with `redact` first.
